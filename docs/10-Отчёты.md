# Отчёты и производительность

Маршрут отчёта, ответ и формулы метрик, разрез по транспорту, правила периода и валюты, лимит частоты, конфигурация и бенчмарк этапа M8. Требования — в [ЧТЗ - Отчёты и производительность](<../.github/docs/Техническое задание/Отчёты и производительность/ЧТЗ - Отчёты и производительность.md>); схема и индексы — в [02-Схема-данных.md](02-Схема-данных.md), планы и замеры — в [Производительность/README.md](Производительность/README.md), индексы — в [ADR-0010](adr/ADR-0010-доказательная-оптимизация-отчётов.md), тесты — в [14-Тесты.md](14-Тесты.md).

## Маршрут и доступ

| Параметр | Значение |
|---|---|
| Метод и путь | `GET /api/v1/reports/orders` |
| Имя маршрута | `reports.orders` |
| Группа | общая группа `/api/v1` под `auth:sanctum`; на маршруте — `verified.api` и `throttle:reports_read` |
| Доступ | роль `admin` по ability `reports:read` |
| Лимит частоты | `reports_read`, ключ — идентификатор пользователя |
| Коды ответов | 200, 401, 403, 409, 422, 429 |

Правило роли — в домене: `Role::canViewReports()` — `true` только для `admin`, `Role::abilities()` даёт `reports:read`. Gate `reports:read` регистрируется в `AppServiceProvider::configureAuthorization` и вызывает `ReportPolicy::view()`; `OrderReportRequest::authorize()` проверяет эту ability.

Отчёт не фильтруется под роль: `sender`, `courier` и `dispatcher` получают 403 `FORBIDDEN` целиком. Запрос не создаёт и не изменяет строки, не публикует события и не пишет в кэш.

## Путь запроса

Контроллер `ReportController::orders()` берёт период и отчёт; доменная ошибка валюты → 409 на границе HTTP. Данные собирают `OrderReportQuery` (сводный агрегат) и `CourierLoadQuery` (секунды смен), форму ответа задаёт `OrderReportResource` через `ReportMetrics` и `TransportBreakdown`.

## Параметры и границы периода

| Параметр | Обязательность | Правила |
|---|---|---|
| `from` | необязательный | ISO-8601 с датой и временем; начало периода включительно |
| `to` | необязательный | ISO-8601 с датой и временем; окончание исключительно, строго позже `from` |

- Период — полуинтервал `[from, to)`: `from <= moment < to`. То же правило применяется к `requested_at`, `cancelled_at`, `delivered_at` и границам смен.
- Значение без смещения — в таймзоне `config('app.timezone')`; в ответе границы с явным смещением (`DateTimeInterface::ATOM`).
- Значения по умолчанию берутся из `config('reporting.default_period')`: `from` — начало текущего месяца, `to` — текущий момент. Неизвестное правило в конфигурации — ошибка запуска, а не тихий дефолт.
- Одной даты без времени недостаточно: формат проверяется регуляркой по `from` и `to` ещё до построения периода.
- Длительность в абсолютных секундах, переход на летнее время значения не меняет. Предел — `config('reporting.max_period_days')` (366 дней), превышение — 422 `REPORT_PERIOD_TOO_LONG` с пределом в пояснении; `to <= from` — 422 `VALIDATION_FAILED` с сообщением у поля `to`.
- `period.days` — целые сутки от абсолютной длительности, для отображения; границы задаёт пара `from`/`to`.

## Состав ответа и формулы метрик

Ответ — `period`, `currency`, `totals`, `by_transport`, `couriers`. Деньги — в минорных единицах, форматирование на клиенте. Округление половина вверх (`App\Domain\Reporting\Rounding`): средние и часы — один знак, доли и доставки на курьера — два, `average_check` — целое.

| Поле | Источник и формула | Пустое значение |
|---|---|---|
| `orders_created` | `COUNT(*)` по `delivery_orders`, у которых `requested_at` попадает в период; статус заказа не важен | `0` |
| `orders_cancelled` | `COUNT(*)` по `delivery_orders`, у которых `cancelled_at` не `null` и попадает в период | `0` |
| `orders_delivered` | число различных вручённых заказов: `COUNT(DISTINCT order_id)` по `assignments` со `status = 'delivered'` и `delivered_at` в периоде | `0` |
| `revenue` | `SUM(delivery_orders.price_amount)` по тем же заказам — снимок цены на момент создания, тариф не пересчитывается | `0` |
| `average_check` | `revenue / orders_delivered`, целое, half-up | `null` при `orders_delivered = 0` |
| `average_eta_minutes` | `SUM(eta_minutes) / orders_created` по заказам периода, один знак, half-up | `null` при `orders_created = 0` |
| `active_couriers` | `COUNT(DISTINCT courier_id)` по вручениям периода (`assignments.status = 'delivered'`, `delivered_at` в периоде) | `0` |
| `deliveries_per_courier` | `orders_delivered / active_couriers`, два знака, half-up | `null` при `active_couriers = 0` |
| `by_transport[].share_percent` | `revenue` строки / общая `revenue` × 100, два знака | `0` |
| `by_transport[].rank` | `RANK() OVER (ORDER BY revenue DESC)`; равная выручка даёт равное место с пропуском следующего | — |
| `couriers.shift_hours` | сумма пересечений смен с периодом / 3600, один знак; открытая смена обрезается правой границей, смена, начавшаяся до периода, — левой, отрицательные пересечения отбрасываются | `0.0` |

Что важно в трактовке:

- вручения и выручка — по метке `assignments.delivered_at`, не по статусу заказа: `delivery_orders` метку вручения не хранит;
- созданный до периода и вручённый в нём заказ входит в `orders_delivered` и `revenue`, но не в `orders_created`; повторные назначения значение не задваивают;
- `orders_cancelled` считается по `cancelled_at`, поэтому отменённый в периоде заказ в выручку не попадает;
- `shift_hours` — все смены, пересекающиеся с периодом, без фильтра по зоне; курьер без вручений неактивен, но его часы входят в сумму;
- блок `couriers` повторяет `totals`: `active_couriers` и `deliveries_per_courier` делегируются тем же объектам и разойтись не могут.

## Разрез по транспорту

`by_transport` — всегда три строки в доменном порядке `TransportType::cases()`: `on_foot`, `light`, `car`, независимо от выручки; отсутствующий тип — нули (`revenue` `0`, доли `0.0`, место по общей выручке). Список типов подаётся в SQL из домена (`unnest`), новый тип — правка перечисления.

Оконные функции считают доли, места и итоги сразу по всем строкам: `SUM(...) OVER ()`, `RANK() OVER (ORDER BY revenue DESC)`; итоги повторяются в каждой строке, приложение берёт их из первой.

## Валюта

Валюта отчёта — `config('reporting.currency')` (по умолчанию `RUB`), из данных не вычисляется. Все суммы — минорные единицы одной валюты, конвертации и курсов нет.

Смешивание валют запрещено: валюты периода собирает тот же сводный запрос, чужая валюта — `ReportCurrencyMismatch` из `OrderReport::fromAggregates()`, ответ 409 `REPORT_CURRENCY_MISMATCH`. Частичного отчёта нет.

## Ошибки

| Код | Код ошибки | Когда |
|---|---|---|
| 401 | `INVALID_CREDENTIALS` | нет токена или токен отозван — общее соглашение `ProblemRenderer` для 401 |
| 403 | `FORBIDDEN` | роль не `admin` или нет ability `reports:read` |
| 409 | `REPORT_CURRENCY_MISMATCH` | в агрегатах периода встречена чужая валюта |
| 422 | `VALIDATION_FAILED` | битая дата, дата без времени, `to <= from` |
| 422 | `REPORT_PERIOD_TOO_LONG` | длительность больше `reporting.max_period_days`; предел указан в `detail` и в `errors.to` |
| 429 | `RATE_LIMITED` | превышен лимит `reports_read`; заголовки лимита как у остальных маршрутов |

Форма ответа — `application/problem+json` (`type`, `title`, `status`, `detail`, `instance`, `code`, `errors`); текст SQL, имена индексов и подробности базы не попадают.

## Лимит частоты

`config/rate_limits.php`, ключ `reports_read`: `attempts = 30`, `decay_seconds = 60` (`RATE_LIMIT_REPORTS_READ_ATTEMPTS`, `RATE_LIMIT_REPORTS_READ_DECAY`). Ключ — идентификатор пользователя: серии не проходят даже со сменой токена. Лимит срабатывает раньше проверки прав.

## Конфигурация

`config/reporting.php`:

| Ключ | Переменная окружения | По умолчанию | Назначение |
|---|---|---|---|
| `currency` | `REPORTING_CURRENCY` | `RUB` | валюта отчёта |
| `max_period_days` | `REPORTING_MAX_PERIOD_DAYS` | 366 | предельная длительность периода в днях |
| `default_period.from` | `REPORTING_DEFAULT_PERIOD_FROM` | `start_of_month` | начало периода по умолчанию |
| `default_period.to` | `REPORTING_DEFAULT_PERIOD_TO` | `now` | окончание периода по умолчанию |
| `benchmark.orders` | `REPORTING_BENCHMARK_ORDERS` | 100000 | размер набора бенчмарка |
| `benchmark.runs` | `REPORTING_BENCHMARK_RUNS` | 20 | число замеров сервиса |
| `benchmark.environments` | `REPORTING_BENCHMARK_ENVIRONMENTS` | `local,testing` | окружения, где допустимо наполнение |

Литералов валюты, длительности периода, лимита частоты и размера набора в коде нет — только `config()`. Типы транспорта для разреза — доменное перечисление.

## Как считается

Отчёт выполняет не более двух SQL:

1. **Сводный агрегат** (`OrderReportQuery`, один `WITH`): CTE `params`, `types` (`unnest` доменного списка с порядком), `delivered_assignments`, `delivered_orders` (вручённые заказы с типом и ценой), `created` (созданные и сумма ETA по типу), `delivered` (вручённые и выручка по типу), `cancelled`, `couriers`, `currencies` и финальный `SELECT` с оконными функциями — итоги, доли, места и валюты приходят здесь же.
2. **Секунды смен** (`CourierLoadQuery`): сумма пересечений смен с периодом одним скаляром.

Приложение не перебирает строки заказов, назначений и смен: сводный запрос отдаёт три строки, сразу превращаемые в доменные объекты. Eloquent-модели не гидратируются, пагинации и `OFFSET` нет.

Число запросов проверяет тест через `DB::listen`: считаются операторы с `SELECT`/`WITH` (сводный запрос — CTE), служебные команды транзакций (`BEGIN`, `COMMIT`, `SAVEPOINT`, `RELEASE`, `ROLLBACK`, `SET`, `SHOW`) пропускаются. Утверждение — ровно два запроса на малом и на большом наборе. Бенчмарк печатает то же: `sql_queries = 2`.

## Бенчмарк

```sh
docker compose exec app php artisan reporting:benchmark --orders=100000 --runs=100 --json
docker compose exec app php artisan reporting:benchmark --orders=100000 --runs=100 --explain
docker compose exec app php artisan reporting:benchmark --orders=100000 --runs=100 --explain --json --with-indexes
```

| Флаг | Назначение |
|---|---|
| `--orders` | размер набора заказов (по умолчанию из конфигурации) |
| `--runs` | число замеров сервиса |
| `--seed` | зерно детерминированного генератора (по умолчанию 42) |
| `--explain` | снимает `EXPLAIN (ANALYZE, BUFFERS)` для отчёта, загрузки курьеров, очереди диспетчера и кабинета отправителя |
| `--with-indexes` | создаёт временные кандидаты индексов на время замера и удаляет их после |
| `--json` | вывод в JSON |
| `--keep` | не удалять набор после прогона |

- Наполнение только в окружениях из `reporting.benchmark.environments` (`local`, `testing`); иначе команда отказывает до изменений в базе с кодом 1.
- Набор строится детерминированно: SQL с `generate_series`, `setseed` от `--seed`, без фабрик и сети. Признаки набора — `BENCH-` в номере заказа и коде зоны, `@benchmark.local` в почте.
- По умолчанию набор удаляется в `finally`; остатки прошлого прогона (в том числе после `--keep`) вычищаются в начале по маркеру. Оставшиеся строки бенчмарка — код 2.
- Замер с `SET jit = off`: компиляция JIT делает его нестабильным. После наполнения — `VACUUM (ANALYZE)`; внутри транзакции (тесты `RefreshDatabase`) `VACUUM` запрещён, там только `ANALYZE`.
- Отчётный период замера — 30 дней, заказы раскладываются по более широкому окну генерации.
- Вывод: окружение, версия PostgreSQL, `seed`, размеры набора, число замеров, `p50/p95/min/max`, число SQL, созданные кандидаты и планы при `--explain`.

Коды возврата: 0 — замер выполнен, 1 — окружение не разрешает наполнение, 2 — ошибка или остались данные бенчмарка.

## Что не входит

- Выгрузка отчёта в файл (CSV, XLSX) — расширение этапа, ориентировочно M10.
- Экран отчёта и его компоненты в интерфейсе — M9.
- Кэширование агрегатов, материализованные представления, read-model, инкрементальный и фоновый пересчёт — не входят.
- Отчёты по зонам, тарифам, отправителям и отдельным курьерам; BI и экспорт во внешние хранилища — не входят.
- Новых таблиц нет: журнала запросов отчёта и аудита просмотра на этапе не появляется.
- Конвертация валют и курсы — не входят; отчёт строится в одной валюте.
