# Доступ, роли и профили

Поведение этапа M1: регистрация, вход и выход, восстановление пароля, роли, профили, политики доступа, формат ошибок, лимиты и токены. Требования — в [ЧТЗ - Основа и доступ](<../.github/docs/Техническое задание/Основа и доступ/ЧТЗ - Основа и доступ.md>).

## Роли и права

| Роль | `role` | Профиль | Что может на M1 | Разрешения токена (`abilities`) |
|---|---|---|---|---|
| Отправитель | `sender` | `sender_profiles` | читать свой профиль; менять имя, телефон, компанию, адрес по умолчанию | `orders:read`, `orders:write` |
| Курьер | `courier` | `courier_profiles` | читать свой профиль; менять только имя | `orders:read`, `courier` |
| Диспетчер | `dispatcher` | нет | читать свой профиль; изменение через API недоступно | `orders:read`, `dispatch` |
| Администратор | `admin` | нет | читать свой профиль; изменение через API недоступно | `orders:read` |

Права роли — перечисление `App\Domain\Identity\Role`: `canCreateOrders`, `canDispatch`, `canHandleAssignments`, `canManageReferences`, `hasSenderProfile`, `canEditOwnProfile`, `abilities()`. На M1 из `abilities` используются только чтение и запись профиля, остальные выданы авансом (ЧТЗ, раздел 6).

## Жизненный цикл доступа

1. **Регистрация.** `POST /api/v1/auth/register` создаёт аккаунт и пустой профиль отправителя в одной транзакции; роль не передаётся — модель и база выставляют `sender`. Письмо подтверждения ставится в очередь после фиксации. Ответ — 201 и `Location` с адресом `/api/v1/profile`.
2. **Письмо.** Подписанная ссылка на 60 минут; хеш в ссылке — `sha1(email)`.
3. **Подтверждение.** `GET|POST /api/v1/auth/email/verify/{id}/{hash}`: подпись проверяет `signed`, затем хеш сверяется с адресом. Повтор валидной ссылки — 200 без изменения даты; истёкшая ссылка и несуществующий пользователь неразличимы — 403 `INVALID_SIGNATURE`.
4. **Вход.** `POST /api/v1/auth/login` проверяет пароль и выдаёт токен Sanctum с разрешениями роли.
5. **Личные действия.** Запрос с заголовком `Authorization: Bearer <token>`.
6. **Выход.** `POST /api/v1/auth/logout` — 204, отзывается только токен текущего запроса.

### Что доступно неподтверждённому пользователю

| Действие | Маршрут | Результат |
|---|---|---|
| Вход | `POST /api/v1/auth/login` | 200, токен выдаётся |
| Повторная отправка письма | `POST /api/v1/auth/email/resend` | 202 |
| Чтение своего профиля | `GET /api/v1/profile`, `GET /api/v1/users/{свой id}` | 200, `email_verified_at` = `null` |
| Изменение профиля | `PATCH /api/v1/profile` | 403 `EMAIL_NOT_VERIFIED` |

Обоснование: ЧТЗ (5.4) относит «свой профиль» к действиям неподтверждённого пользователя, FR-IDN-107 запрещает «личные разделы, кроме повторной отправки письма»; чтение нужно для показа адреса и статуса подтверждения, запись закрыта middleware `verified.api`.

## Маршруты этапа

| Метод | Путь | Middleware и лимит | Успех | Ошибки |
|---|---|---|---|---|
| POST | `/api/v1/auth/register` | `throttle:auth-register` | 201 + `Location` | 422 `VALIDATION_FAILED`, 429 `RATE_LIMITED` |
| GET, POST | `/api/v1/auth/email/verify/{id}/{hash}` | `signed` | 200 | 403 `INVALID_SIGNATURE` |
| POST | `/api/v1/auth/email/resend` | `auth:sanctum`, `throttle:auth-email-resend` | 202 | 401 `INVALID_CREDENTIALS`, 429 `RATE_LIMITED` |
| POST | `/api/v1/auth/login` | лимит входа в операции (без throttle-middleware) | 200 + `token` | 401 `INVALID_CREDENTIALS`, 422 `VALIDATION_FAILED`, 429 `RATE_LIMITED` + `Retry-After` |
| POST | `/api/v1/auth/logout` | `auth:sanctum` | 204 | 401 `INVALID_CREDENTIALS` |
| POST | `/api/v1/auth/password/forgot` | `throttle:auth-password-forgot` | 202 всегда | 422 `VALIDATION_FAILED`, 429 `RATE_LIMITED` |
| POST | `/api/v1/auth/password/reset` | `signed` | 200 | 403 `INVALID_SIGNATURE`, 422 `VALIDATION_FAILED` |
| GET | `/api/v1/profile` | `auth:sanctum` | 200 | 401 `INVALID_CREDENTIALS` |
| PATCH | `/api/v1/profile` | `auth:sanctum`, `verified.api` | 200 | 401 `INVALID_CREDENTIALS`, 403 `EMAIL_NOT_VERIFIED` / `FORBIDDEN`, 422 `VALIDATION_FAILED` |
| GET | `/api/v1/users/{user}` | `auth:sanctum` | 200 (свой id) | 401 `INVALID_CREDENTIALS`, 404 `NOT_FOUND` (чужой и несуществующий) |

Таблица ограничена маршрутами M1 (доступ и профили). Стоимость и ETA — `POST /api/v1/estimates` с `auth:sanctum`, `verified.api`, `throttle:pricing-estimate` ([04-Стоимость-и-ETA.md](04-Стоимость-и-ETA.md)).

Сброс пароля не раскрывает существование аккаунта: для известного и неизвестного адреса тело и 202 совпадают, письмо — только владельцу.

## Профили отправителя и курьера

`ProfileResource` — публичные данные из `UserResource` (`id`, `name`, `email`, `role`, `email_verified_at` в ISO 8601 или `null`) и `profile`: профиль роли либо `null`.

| Поле | Таблица | Кто меняет через API | Правила |
|---|---|---|---|
| `name` | `users` | отправитель, курьер | 2–255 символов |
| `email`, `role`, `email_verified_at` | `users` | никто | только чтение |
| `phone` | `sender_profiles` | отправитель | `nullable`, до 32 символов |
| `company` | `sender_profiles` | отправитель | `nullable`, до 255 символов |
| `default_address` | `sender_profiles` (jsonb) | отправитель | объект из `district`, `street`, `house`, `latitude` (−90…90), `longitude` (−180…180) |
| `transport_type`, `light_vehicle_kind`, `is_active` | `courier_profiles` | никто (назначает администратор на следующем этапе) | только чтение |

Запрещённые поля возвращают 422 `VALIDATION_FAILED`, а не игнорируются:

- `role` — смена роли через профиль закрыта (FR-IDN-310);
- `transport_type`, `light_vehicle_kind`, `is_active` — транспорт и активность администрируются;
- `phone`, `company`, `default_address` — для курьера, у него редактируется только имя.

Диспетчеру и администратору `PATCH /api/v1/profile` недоступен целиком: политика `updateProfile` не пропускает их до проверки полей — 403 `FORBIDDEN`.

Схема и домен согласованы по транспорту: `users.role` — ограниченный набор, по умолчанию `sender`; `light_vehicle_kind` только при `transport_type = light` (CHECK `courier_profiles_light_kind_check`, `TransportType::assertAccepts`, `InvalidTransportCombination`); `user_id` в `sender_profiles` и `courier_profiles` уникален. Профиля отправителя нет (аккаунт заведён вручную) — `PATCH` создаёт его при первом изменении.

## Политики доступа

- `App\Policies\UserPolicy::viewProfile` — только владелец; `updateProfile` — владелец и роль с `canEditOwnProfile()` (отправитель, курьер).
- Правило владения сравнивает идентификаторы, а не объекты моделей.
- `GET /api/v1/users/{user}` на чужой идентификатор — 404 `NOT_FOUND`, не 403 (FR-API-106); тело совпадает с ответом на несуществующий, кроме `instance` (путь запроса).
- Проверки ролей не дублируются в контроллерах: просмотр — политика, изменение дополнительно закрыто `verified.api`.

## Формат ошибок

Все ошибки API — `Content-Type: application/problem+json` (RFC 7807) из одного места, `App\Http\Problem\ProblemRenderer`.

| Поле | Содержимое |
|---|---|
| `type` | URI `{API_PROBLEM_TYPE_BASE}/{CODE}`, база по умолчанию `https://courier.example/problems` |
| `title` | короткий заголовок на русском (`lang/ru/errors.php`) |
| `status` | HTTP-статус |
| `detail` | пояснение на русском |
| `instance` | путь запроса, например `/api/v1/profile` |
| `code` | машиночитаемый код |
| `details` | массив `{field, message}`; заполняется для ошибок валидации, иначе пустой |

Коды этапа:

| Код | Статус | Когда |
|---|---|---|
| `VALIDATION_FAILED` | 422 | данные не прошли проверку, запрещённое поле, несовпадение пароля |
| `INVALID_CREDENTIALS` | 401 | нет или недействителен токен; неверный email или пароль |
| `EMAIL_NOT_VERIFIED` | 403 | неподтверждённая почта на `verified.api` |
| `RATE_LIMITED` | 429 | превышен лимит; приходит `Retry-After` |
| `FORBIDDEN` | 403 | роль не может менять профиль, нет прав политики |
| `NOT_FOUND` | 404 | чужой или несуществующий идентификатор |
| `INVALID_SIGNATURE` | 403 | подпись неверна, истекла или ссылка уже использована |
| `INTERNAL_ERROR` | 500 | непредвиденная ошибка без трассировки и внутренних сообщений |

Кириллица и слеши не экранируются: флаги `App\Http\ApiResponse::JSON_FLAGS` действуют и для ответов, и для ошибок.

## Лимиты частоты

| Лимит | Ключ | По умолчанию | Переменные окружения |
|---|---|---|---|
| `auth-login` (в операции входа) | email в нижнем регистре + IP | 5 попыток / 60 с | `RATE_LIMIT_LOGIN_ATTEMPTS`, `RATE_LIMIT_LOGIN_DECAY` |
| `auth-register` | IP | 10 / 3600 с | `RATE_LIMIT_REGISTER_ATTEMPTS`, `RATE_LIMIT_REGISTER_DECAY` |
| `auth-email-resend` | идентификатор пользователя | 3 / 600 с | `RATE_LIMIT_EMAIL_RESEND_ATTEMPTS`, `RATE_LIMIT_EMAIL_RESEND_DECAY` |
| `auth-password-forgot` | IP | 3 / 600 с | `RATE_LIMIT_PASSWORD_FORGOT_ATTEMPTS`, `RATE_LIMIT_PASSWORD_FORGOT_DECAY` |

Значения — из `config/rate_limits.php` в момент запроса, ключи лимитов — в `AppServiceProvider`. Вход иначе: счётчик ведёт `App\Actions\Identity\LoginAttemptLimiter`, увеличивая его **только при неудаче**; успешный вход сбрасывает. Ключ включает email, поэтому лимит одного адреса не блокирует остальные.

## Токены

- Токены — Sanctum personal access tokens с именем `api-v1`; передаются заголовком `Authorization: Bearer <token>`.
- Набор разрешений — из `Role::abilities()` в момент входа (см. таблицу ролей).
- Срок жизни токена не ограничивается (допущение 2 ЧТЗ).
- Выход отзывает только токен текущего запроса; токены других устройств работают.
- Сброс пароля отзывает все токены пользователя: старые сессии требуют повторного входа.

## Сроки ссылок

| Ссылка | Срок | Где настраивается |
|---|---|---|
| Подтверждение почты | 60 минут | `EMAIL_VERIFICATION_EXPIRE` (`config/auth.php`, `verification.expire`) |
| Сброс пароля | 60 минут | `PASSWORD_RESET_EXPIRE` (`config/auth.php`, `passwords.users.expire`) |

Обе ссылки подписанные (`signed`); токен сброса одноразовый — брокер удаляет его после смены, повтор — 403 `INVALID_SIGNATURE`. Новый токен — не чаще раза в 60 секунд (`passwords.users.throttle`)

## Что появится дальше (M2+)

Наборы `orders:write`, `dispatch`, `courier` заработают на этапах заказов, назначений и доставки; там же роль и журнал `role_changes`, транспорт и активность курьера, проверка адреса по зонам. Маршрутов пока нет — таблицы и перечисления существуют.
