## Путь события

| Этап | Что происходит |
|---|---|
| операция M4–M6 | в транзакции изменения заказа, назначения или смены — `INSERT outbox_messages`; затем `COMMIT` |
| публикатор | `outbox:publish` по расписанию под `Cache::lock('outbox:publish')`: `SELECT … FOR UPDATE SKIP LOCKED` |
| доставка | `Redis Streams` (`events.orders`, `events.contacts`) → `notifications:consume`: `INSERT inbox_messages` → `INSERT notification_dedup` → `INSERT notifications (created)` → `COMMIT` → `XACK` → `notifications:send` → email / push / Telegram → `notification.sent` / `notification.failed` |
| фиксация | `UPDATE published_at` только после успеха; сбой — `attempts+1`, `last_error`, `available_at`; `attempts = max` — необработанное |

Событие пишется в `outbox_messages` в той же транзакции, что и изменение состояния (`Order\CreateOrder`, `Order\CancelOrder`, `Dispatch\*`); незавершённая транзакция публикатору не видна. При `events.transport=redis` событие уходит в Redis Streams, сервис создаёт строки журнала в транзакции Inbox, подтверждает после `COMMIT`, а отправляет собственный поллер.

## Outbox

### Строка события

Таблица `outbox_messages` (базовая миграция M4 и расширение `2026_11_05_100001_extend_outbox_messages_for_publishing.php`):

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `bigserial` | технический ключ строки |
| `message_id` | `uuid`, `NOT NULL`, `DEFAULT gen_random_uuid()` | идентификатор сообщения; выдаёт база |
| `aggregate_type` | `varchar(64)` | владелец агрегата: `order` или `courier_shift` |
| `aggregate_id` | `bigint` | идентификатор агрегата; внешнего ключа нет — агрегаты разные |
| `event_type` | `varchar(64)` | тип события из реестра (`order.created` и т. д.) |
| `payload` | `jsonb` | тело события без персональных данных |
| `published_at` | `timestamptz`, `NULL` | отметка успешной передачи всем слушателям |
| `attempts` | `smallint`, `DEFAULT 0` | число неудачных попыток передачи |
| `last_error` | `text`, `NULL` | код причины последнего сбоя |
| `available_at` | `timestamptz`, `NOT NULL` | момент, с которого строку можно брать |
| `created_at` | `timestamp`, `DEFAULT now()` | момент записи события |

Индексы и ограничения: уникальный `outbox_messages_message_id_unique (message_id)`; частичный `outbox_messages_pending_index (available_at, created_at, id) WHERE published_at IS NULL` — по нему идёт выборка публикатора; прежний `(published_at, created_at)` сохранён; CHECK `outbox_messages_attempts_check (attempts >= 0)`. Модель `App\Models\Order\OutboxMessage` приводит `available_at` и `published_at` к UTC и заполняет `available_at` моментом создания.

### Состояния сообщения

| Состояние | Условие в данных | Кто видит | Переход |
|---|---|---|---|
| ожидает | `published_at IS NULL`, `attempts < max`, `available_at <= now()` | публикатор, `outbox:status` | публикуется при следующем проходе |
| публикуется | строка забрана `FOR UPDATE SKIP LOCKED` в текущей транзакции | только публикатор | опубликовано или ожидает (с backoff) |
| опубликовано | `published_at IS NOT NULL` | `outbox:status`, журнал | терминальное; очистка по сроку хранения не вводится |
| не обработано | `published_at IS NULL`, `attempts >= max`, `last_error` заполнен | `outbox:status`, `outbox:failed` | ручной разбор; автоматического повтора нет |

Состояние «публикуется» не хранится колонкой: это время жизни транзакции и блокировки, поэтому «зависших» строк не остаётся даже после падения процесса.

### Публикатор

`App\Services\Events\OutboxPublisher` реализует `EventPublisher` и выполняет проход `run(?int $limit = null)`:

проход под `Cache::lock('outbox:publish', $lockTtlSeconds)`; если блокировку держит другой воркер — `PublishResult::locked()` (команда завершается кодом 0); пачка: `WHERE published_at IS NULL AND attempts < max AND available_at <= now()`, `ORDER BY created_at, id`, `LIMIT`, `lock('for update skip locked')`; событие идёт в шину во вложенной транзакции, слушатель — в своей транзакции-сейве, отказ одного откатывает только его; `published_at` — только после приёма всеми слушателями; сбой увеличивает `attempts`, пишет `last_error = OUTBOX_PUBLISH_FAILED` и сдвигает `available_at` по ряду backoff (последний элемент повторяется); при `attempts >= publish_max_attempts` строка ждёт ручного разбора; `EVENT_TYPE_UNKNOWN` — событие помечается опубликованным без повтора (в журнал — `code`, `message_id`, `event_type`); `EVENT_PAYLOAD_INVALID` — `attempts` сразу до предела, `last_error = EVENT_PAYLOAD_INVALID`.
Параметры читаются из `config/events.php` один раз при создании объекта (`AppServiceProvider`); литералов размера пачки, числа попыток, задержек и TTL в коде нет.

## Реестр и контракт событий

Домен событий — `App\Domain\Events`; о фреймворке, базе и конфигурации не знает.

| Класс | Ответственность |
|---|---|
| `EventType` | одиннадцать типов: шесть событий заказа (`order.created`…`order.cancelled`), две смены курьера, `user.contact_changed` и обратные `notification.sent`, `notification.failed`; несовместимое изменение — новый тип |
| `AggregateType` | владелец агрегата: `order` или `courier_shift`; выводится из типа события |

| `EventEnvelope` | неизменяемый конверт для шины: `message_id`, `event_type`, `schema_version`, `occurred_at`, `aggregate_type`, `aggregate_id`, `payload` |

Общий состав payload события заказа собирает `App\Services\Events\OrderEventPayload`: `event_id` (равен `message_id` строки Outbox, поэтому повторная публикация сохраняет идентификатор), `order_id`, `tracking_code`, `sender_id`, `status`, `occurred_at`, `locale`. ## Шина и карта слушателей

`App\Services\Events\LocalEventBus` реализует `EventBus` с картой «тип события → слушатели» из `AppServiceProvider`; карта пуста — единственный отправитель сервис (`FR-NTF-406`), поэтому `LocalEventBus` остаётся транспортом `events.transport=in-memory` для тестов и контрактных проверок.
Слушатели вызываются изолированно: исключение логируется с `code = EVENT_LISTENER_FAILED`, `message_id`, `event_type`; если отказал хотя бы один, шина выбрасывает `EventDeliveryFailed` (`OUTBOX_PUBLISH_FAILED`) и публикатор не ставит `published_at` — доставка повторится. Замена шины брокером домен и операции не меняет.

## Транспорт событий (M11)

Контракт `App\Services\Events\Contracts\EventBus` с четырьмя операциями: `publish`, `consume`, `ack`, `reclaim`. Выбор реализации — `AppServiceProvider` по `config('events.transport')`; неизвестное значение — ошибка конфигурации, а не тихий выбор по умолчанию.

| Реализация | Механика | Когда используется |
|---|---|---|
| `LocalEventBus` | карта «тип события → слушатели» в процессе, синхронный вызов; `dispatch` нужен тестам и локальному пути | `events.transport=in-memory` |
| `RedisStreamEventBus` | `XADD` в поток, `XREADGROUP` пачкой, `XACK` после фиксации эффекта, `XAUTOCLAIM` для сообщений старше `pending_idle_seconds` | `events.transport=redis` (по умолчанию) |
| `RabbitMqEventBus` | `basic_publish` в exchange `topic` с ключом «домен + тип события», чтение `basic_get` без автоподтверждения, `ack` после фиксации эффекта, `basic_reject` в DLX после предела попыток | `events.transport=rabbitmq` (опция, профиль compose `broker`) |
| Поток (`events.streams`) | Имя по умолчанию | Что несёт | Кто читает |
|---|---|---|---|
| `orders` | `events.orders` | события заказов | сервис оповещений, группа `consumer_group` |
| `contacts` | `events.contacts` | `user.contact_changed` — единственный контракт с персональными данными | сервис оповещений, отдельное имя потребителя |
| `notifications` | `events.notifications` | обратные события `notification.sent` и `notification.failed` | монолит, группа `status_consumer_group` (`courier`) |

Правила транспорта:

Контракт `EventBus`: `publish`, `consume`, `ack`, `reclaim`; `ack` — после фиксации эффекта, доставка «хотя бы один раз», перевыдача по `pending_idle_seconds`, `stream_prefix` — префикс потоков; при недоступности Redis проход возвращает `degraded` с кодом `EVENT_TRANSPORT_UNAVAILABLE`, публикация пробрасывает исключение (публикатор не ставит `published_at` и повторяет по backoff). Остальное — [ADR-0015](adr/ADR-0015-транспорт-событий.md) и раздел «Транспорт событий».

### Опциональный брокер RabbitMQ (M13)

Вторая реализация тех же контрактов: `RabbitMqEventBus` в монолите и `RabbitMqEventStream` в сервисе. Выбор — по `EVENTS_TRANSPORT` / `NOTIFICATIONS_TRANSPORT`; неизвестное значение останавливает старт (проверяет `TransportGuardTest`).

| Что | Как устроено |
|---|---|
| exchange | тип `topic`; имя из `events.rabbitmq.exchange` / `notifications.transport.rabbitmq.exchange` (по умолчанию `events`) |
| ключ маршрутизации | домен и полный тип события (`orders.order.created`); соответствие «префикс типа → домен» в конфигурации (`order` и `courier` → `orders`, `user` → `contacts`, `notification` → `notifications`) |
| очередь потребителя | имя `<поток>.<группа>`: `events.orders.<группа>`, `events.contacts.<группа>`, `events.notifications.<группа>`; привязка — `<домен>.#` |
| подтверждение | `ack` только после фиксации эффекта; инфраструктурная ошибка — `nack`/`requeue`; после `max_attempts` — `basic_reject` в DLX |
| TTL и DLX | per-message TTL `message_ttl_seconds` и TTL очереди; истёкшее и исчерпавшее попытки сообщение уходит в `dlx_exchange` и очередь `notifications.dlq` |
| разбор DLX | второго разбора нет: `DeadLetterRedriver` возвращает сообщения в основной exchange, дальше работают Inbox, дедупликация и `dlq_entries`; число возвратов конечно (`x-redriven`) |
| недоступность брокера | публикатор не ставит `published_at` и повторяет по backoff; `/health` добавляет проверку `broker`, `notifications:broker-health` показывает соединение, очереди и DLQ; события не теряются |
| профиль compose | `rabbitmq` поднимается только профилем `broker` (`docker compose --profile broker up -d rabbitmq`, management UI на `15672`); без профиля основной запуск идёт на Redis |
| расширение PHP | клиент `php-amqplib` v3 требует `ext-sockets`: образы обоих приложений ставят `sockets`, без него подключение невозможно |

Параметры подключения читаются только из окружения (`RABBITMQ_*`), секреты не попадают в журнал, метрики, ошибки и DLQ. Совпадение поведения транспортов подтверждает паритетный набор `TransportParityTest` в обоих проектах.

## Контракты JSON Schema

Единственный экземпляр схем — `contracts/notifications/`: восемь файлов `*.v1.json` и README с таблицей «файл — `event_type` — поток» ([README контрактов](../contracts/notifications/README.md)). Копий нет: монолит и сервис читают один каталог (сервис получает его монтированием только для чтения).

`App\Services\Events\JsonSchemaValidator` читает `events.schema_path`, один раз за процесс строит перечень «слаг — версия — файл» и проверяет конверт с payload до передачи в транспорт. Имя файла — из типа события: точки и подчёркивания в дефисы плюс версия (`order.picked_up` → `order-picked-up.v1.json`). `EventContractUnknown` — контракт есть, версии нет; `EventContractInvalid` — конверт или payload не по схеме; событие не теряется — строка остаётся в `outbox_messages` и видна в `outbox:failed`. В ошибке нет персональных данных: тип, версия, ключевое слово и путь поля. У `order.cancelled` и смен курьера контрактов M11 нет. Совместимость аддитивная: новое обязательное поле или смена смысла — `*.v2.json`, `*.v1.json` живёт до миграции потребителей.
Поток выбирает `App\Services\Events\EventStreamRouter`: контакты — в собственный поток, обратные события — в поток уведомлений, остальные события заказа — в поток заказов; персональные данные `user.contact_changed` не смешиваются с событиями заказа. Событие пишет `App\Services\Events\UserContactChangedOutbox` в транзакции операции регистрации и смены почты: сервис получает адрес и язык вместе с изменением, а не читает чужую базу.

## Обратные события и проекция (M11)

Сервис публикует `notification.sent` и `notification.failed` в поток `events.notifications` из собственного Outbox. Монолит потребляет их командой `notifications:consume-status --once`; в расписании задача идёт с интервалом `events.status_consume_interval_seconds` и группой `courier`, поэтому отметки о прочтении потоков заказов и уведомлений независимы.
`App\Services\Notifications\NotificationStatusProjector` применяет событие через Inbox монолита и пишет `order_notification_status` через `insertOrIgnore`: уникальные индексы `notification_id` и `source_event_id` держат «ровно один эффект», проверки «есть ли уже» нет. Неизвестный тип логируется с кодом `EVENT_CONTRACT_UNKNOWN` и подтверждается без эффекта. `correlation_id` обратного события попадает в журнал монолита: цепочка «запрос → событие → уведомление → проекция» прослеживается по одному идентификатору.

## Inbox

`App\Services\Events\Inbox` обеспечивает «ровно один эффект» на пару «событие — обработчик».

Ключ — уникальная пара `(message_id, handler)` в `processed_messages`; имя обработчика задаёт вызывающий слой и не меняется при рефакторинге (так отсекается повтор обратного события проекцией статусов). Порядок строгий: вставка отметки через `insertOrIgnore` (`ON CONFLICT DO NOTHING`), затем эффект — в одной транзакции. Если вставка вернула 0 строк, обработчик уже отработал: `InboxResult::Skipped`, эффекта и ошибки нет. Если эффект упал, откатываются и отметка, и эффект. `processed_at` — `timestamptz`, момент в UTC; `created_at` ведётся приложением и используется для очистки по сроку хранения.

| `order.failed` | email | — |
| `order.cancelled` | email | push (только при наличии назначения) |

каналы, выключенные в `enabled_channels`, из матрицы отбрасываются; правило без каналов в политику не попадает; `requires_assignment` ограничивает роль курьера для `order.cancelled`: уведомление уходит только если у заказа было назначение; событий смен курьера в матрице нет: они уведомлений не порождают; роли получателей — `sender` и `courier`; это не роли доступа пользователя; матрица остаётся единственным дефолтом (FR-NTF-459): сохранённая строка предпочтения заменяет каналы типа события целиком, а её отсутствие возвращает каналы матрицы.
Эффект события собирает `App\Services\Notifications\OrderEventProcessor` в транзакции Inbox. Получателей определяет `RecipientResolver`: отправитель — из `payload.sender_id`, курьер — из `payload.courier_id` события назначения; у `order.cancelled` назначения в payload нет, поэтому курьер ищется по собственному журналу сервиса (самая поздняя строка этого заказа с ролью `courier`). Нераспознанный получатель и отсутствие шаблона дают предупреждение (`NOTIFICATION_RECIPIENT_UNKNOWN`, `NOTIFICATION_TEMPLATE_NOT_FOUND`) без исключения и без строки журнала.

### Предпочтения получателя (M12)

Источник истины — `notification_preferences` сервиса: строка на пару «пользователь — тип события» с каналами (`channels jsonb`), окном тихих часов (`quiet_hours jsonb`), локалью и меткой `critical_override`. Монолит предпочтения не хранит и не кэширует: экран читает и сохраняет их через служебный API (`GET` и `PATCH /api/v1/preferences`).

| Что | Правило |
|---|---|
| дефолт | строки нет — действуют каналы матрицы для роли получателя; API отдаёт строку с `source = default` |
| сохранение | `PATCH` проверяет весь набор до записи и пишет строки в одной транзакции: при ошибке не сохраняется ни одна строка |
| сброс | `reset: true` удаляет строку, тип события снова получает дефолт матрицы |
| отключение | `channels: []` у некритичного события означает «не уведомлять»: строк журнала и обратного события нет |
| критичные события | `order.delivered` и `order.failed` нельзя оставить без email: набор без `email` отклоняется `422 PREFERENCE_CRITICAL_CHANNEL_REQUIRED` |
| роль | необязательный `role` сужает выдачу до типов событий роли; без него API отдаёт объединение наборов |
| валидация | каналы — подмножество `enabled_channels`, локаль — из `locales.supported`, окно — `HH:MM` и таймзона из `DateTimeZone::listIdentifiers()`; ошибки полей — `422` в `application/problem+json` |

Наборы типов событий по ролям — конфигурация сервиса (`sender_event_types`, `courier_event_types`, `dispatcher_event_types`, `admin_event_types`): у диспетчера и администратора пусты, поэтому экран показывает только тихие часы и привязку Telegram. Перечня «роль → типы событий» в монолите нет (`tests/Arch/NotificationPreferencesGuardTest.php`). Изменение предпочтений журнал не пересчитывает.

### Цепочка каналов и замещение (M12)

`NotificationPolicyResolver::resolveFor()` собирает каналы: сохранённая строка предпочтения авторитетна, её отсутствие даёт матрицу; отбрасываются каналы вне `enabled_channels` и недоступные заранее (`Channels\ChannelAvailability`) — email без адреса, Telegram без подтверждённой привязки, push при выключенном канале; итог по `notifications.preferences.channel_priority` (`push,telegram,email`), email последний. Глубину цепочки считает `App\Domain\Notifications\FallbackChain` по ссылкам (предел `max_fallback_depth`, по умолчанию 3); второй строки того же канала нет — ключ `(event_id, recipient_id, channel)` захватывается до вставки; конец цепочки — email, при недоступности исходная строка остаётся `failed`; `400 chat not found` и `403 bot was blocked by the user` отзывают привязку Telegram; замещение пишется в журнал полями `channel`, `fallback_from`, `event_type`.

| Итог резолвера | Что происходит |
|---|---|
| каналы доступны | по строке `created` на каждый канал; отложенные получают `deferred_until` |
| набор пуст по решению пользователя | строк и обратных событий нет |
| каналы выбраны, но все недоступны | одна строка `failed` с `NOTIFICATION_CHANNEL_UNAVAILABLE` и обратное событие `notification.failed` |

Замещение — штатное поведение: детерминированный отказ (нет чата Telegram, отозванная привязка, `400`/`403` Bot API, отказ провайдера) даёт `failed`, а `ChannelFallback` создаёт строку следующего канала в `created` со ссылкой `fallback_from_notification_id`; инфраструктурный сбой (`429`, `5xx`, таймаут) — `error` и повтор по backoff. Коды — `notifications.preferences.fallback_error_codes`.

### Тихие часы (M12)

Окно — часть строки предпочтения: `{from, to, timezone}`, `from > to` — через полночь, `from == to` недопустимо; `App\Domain\Notifications\QuietHours::deferredUntil()` один раз при создании строки считает ближайшее окончание окна в таймзоне получателя и пишет UTC в `notifications.deferred_until` (изменение настроек строки не переносит). Откладываются только каналы из `notifications.preferences.quiet_hours_channels` (`push,telegram`) — email уходит сразу; `critical_event_types` окно игнорируют; поллер не берёт строку до `deferred_until` и не дублирует её; отложенная строка даёт счётчик `deferred`; моменты — `timestamptz`, в тестах `Carbon::setTestNow`.

| процесс | контейнер `notifications-telegram` под профилем compose `telegram`: long polling не задерживает отправку |

### Состояния и переходы

| Состояние | Значение | Условие | Переход |
|---|---|---|---|
| создано | `created` | строка создана `OrderEventProcessor` или `ChannelFallback` | в очередь |
| в очереди | `queued` | поллер взял строку и увеличил `attempts` | отправлено, ошибка или не отправлено |
| отправлено | `sent` | канал принял сообщение, `sent_at` заполнен | терминальное |
| ошибка | `error` | инфраструктурный сбой, попытки ещё есть | в очередь по backoff или не отправлено |
| не отправлено | `failed` | детерминированный отказ, исчерпание попыток или пустая цепочка каналов | ручной повтор `POST /api/v1/notifications/{id}/retry`: `failed` → `error` |

Набор состояний защищён CHECK базы и enum `App\Domain\Notifications\NotificationStatus`; меняет состояние `App\Services\Notifications\NotificationSender`, каждую попытку фиксирует `NotificationAttemptRecorder` вставкой в `notification_attempts` (уникальная пара `(notification_id, attempt)`). Из `sent` переходов нет; из `failed` автоматических переходов нет.

### Поллер отправки

`App\Services\Notifications\NotificationSendQueue::due()` берёт строки в `created` и `error`, а также брошенные `queued` со `updated_at` старше `sender.retry_after_seconds`; строка не берётся, пока `next_attempt_at` или `deferred_until` в будущем. Готовность по backoff — по последней строке `notification_attempts` и ряду `sender.backoff_seconds` с детерминированным разбросом `backoff_jitter_ratio`; последняя попытка берётся коррелированным подзапросом по индексу `(notification_id, attempt)`. Попытка фиксируется в `notification_attempts`: номер, статус, класс причины (`business`, `infrastructure`, `program`), код и безопасное усечённое сообщение (`attempt_message_limit`); email и телефоны вычищает `AttemptMessageSanitizer`. Бизнес-отказ и программная ошибка (`Error`) дают `failed` без повтора; инфраструктурный сбой — `error` и повтор по backoff; после `sender.max_attempts` — `failed` с сохранённой причиной. `retry_after` лимита Telegram попадает в `next_attempt_at`, поэтому повтор не нарушает лимит провайдера; при успехе и бизнес-отказе значение снимается. Обратное событие `notification.sent` или `notification.failed` пишется в Outbox сервиса в той же транзакции, что и терминальный статус.

### Push-провайдер и токены устройств (M13)

`App\Services\Notifications\Channels\PushChannel` зависит только от контракта `PushProvider`; реализацию выбирает `PushProviderFactory` по `notifications.push.provider`:

| Значение | Реализация | Поведение |
|---|---|---|
| `fake` (по умолчанию) | `FakePushProvider` | пишет сообщение в `push_messages` (`notification_id`, `recipient_id`, `template`, `body`, `sent_at`), в сеть не ходит; получателям из `push.fake_deterministic_fail_recipients` детерминированно отказывает |
| `fcm` | `FcmPushProvider` | FCM HTTP v1 `messages:send` через фасад `Http` без SDK, адресация по активным device-токенам |
| иное | — | ошибка конфигурации при старте |

Правила `fcm`:

токен доступа OAuth2 получает `ServiceAccountFcmTokenSource` по service account JSON; путь и проект — только из окружения (`FCM_PROJECT_ID`, `FCM_CREDENTIALS_PATH`), пустые значения при выбранном `fcm` — ошибка конфигурации; таймаут и число повторов — `FCM_TIMEOUT_SECONDS`, `FCM_RETRY_TIMES`; повторяются только идемпотентные ответы (`429`, `5xx`, таймаут), `Retry-After` учитывается в пределах лимита и передаётся отправителю как `next_attempt_at`; ответ `404`/`410` с причиной `UNREGISTERED` отзывает токен и даёт бизнес-код `NOTIFICATION_DEVICE_UNREGISTERED`, после чего работает замещение каналов; повтор по тому же токену не выполняется; отсутствие активного токена — бизнес-причина `NOTIFICATION_PUSH_TOKEN_MISSING`, DLQ не создаётся (штатное замещение); токен устройства и токен доступа не логируются: в журнал попадают только `fingerprint` и `platform`.
Токены ведутся служебным API: `POST /api/v1/device-tokens` (`201` — создан, `200` — обновлён, `422` — ошибка полей) и `DELETE /api/v1/device-tokens/{id}` (`204` — отозван, `202` — уже отозван, `404` — не найден). Токен уникален глобально; повторная регистрация обновляет владельца, платформу, локаль, версию и `last_seen_at`, ранее отозванный токен снова становится активным. В ответах токен не возвращается.

### Очередь необработанных (DLQ, M13)

Терминальный отказ канала (`notifications.status=failed`) оставляет запись в `dlq_entries` — одна запись на пару `(notification_id, channel)`. Запись создаётся **в той же транзакции**, что статус, строка попытки и событие Outbox сервиса: `NotificationSender::finalize()` вызывает `DlqEntryWriter`, поэтому состояния «статус `failed` без записи» не бывает. Успешная отправка переводит запись того же канала в `resolved` в той же транзакции.

| Состояние | Смысл | Переход |
|---|---|---|
| `open` | отказ зафиксирован, разбор не начат | повтор → `replayed`; истечение срока — удаление командой |
| `replayed` | повтор поставлен, строка журнала снова в `error` | успех → `resolved`; новый терминальный отказ → `open` |
| `resolved` | строка журнала стала `sent` | терминальное, повтор отклоняется |

Запись хранит снимок отказа, а не тело сообщения:

| Поле | Смысл |
|---|---|
| `notification_id`, `channel` | ссылка на строку журнала и канал; пара уникальна |
| `state`, `replay_count`, `last_replayed_at`, `resolved_at` | состояние разбора и учёт повторов |
| `event_id`, `event_type`, `order_id`, `recipient_id`, `recipient_role`, `correlation_id` | снимок события и адресата без персональных данных |
| `error_class`, `error_code`, `attempts`, `failed_at` | причина и номер попытки; момент из транзакции отказа |

дедупликация — уникальный индекс `(notification_id, channel)`, вставка идёт `upsert`; повтор идемпотентен: возвращает **ту же** строку журнала в `error` с плановой задержкой backoff, увеличивает `replay_count` и `last_replayed_at`; второго уведомления и записи нет; повтор разрешён только из `open`; разобранная запись отклоняется `DLQ_ENTRY_ALREADY_RESOLVED` (`409`), отсутствующая — `DLQ_ENTRY_NOT_FOUND` (`404`); отказ одного канала не блокирует остальные: уведомления одного события — разные строки журнала; очистка — только срок хранения `dlq.retention_days` командой `notifications:dlq-purge` и по расписанию; при повторе запись не удаляется.

### Метрики `/metrics` (M13)

`GET /metrics` отдаёт `text/plain; version=0.0.4` за сервисным токеном; без токена — `401` в `application/problem+json`, при `metrics.enabled=false` — `404` тем же форматом.

| Метрика | Тип | Метки | Источник |
|---|---|---|---|
| `notifications_sent_total` | counter | `channel` | инкремент в `NotificationSender::finalize()` |
| `notifications_failed_total` | counter | `channel` | то же |
| `notifications_retried_total` | counter | `channel` | инкремент при попытке с номером больше 1 |
| `notifications_send_duration_seconds` | histogram | `channel`, `le` | фактическое время попытки, включая повтор |
| `notifications_dlq_depth` | gauge | `channel`, `state` | число неразобранных записей `dlq_entries` (`open`, `replayed`) |
| `notifications_consumer_lag_seconds` | gauge | `stream` | consumer group Redis Streams |
| `notifications_consumer_pending` | gauge | `stream` | consumer group Redis Streams |
| `notifications_outbox_oldest_unpublished_seconds` | gauge | — | возраст старейшей строки Outbox сервиса без `published_at` |

`/metrics` дешёвый: счётчики и гистограмма живут в процессе отправки и сбрасываются в общий кэш (`NotificationCounters::flushToCache()`, по умолчанию Redis), «дорогие» gauge считает задача `notifications:metrics-snapshot` с TTL `metrics.snapshot_ttl_seconds`; обработчик читает готовый документ. Метки закрыты белым списком (`metrics.labels`), идентификаторы в них попасть не могут. Недоступный источник не роняет сервис: отдаётся то, что есть, деградация пишется кодом `METRICS_UNAVAILABLE`. Лаг и pending считаются по consumer group **Redis Streams** независимо от транспорта; при `NOTIFICATIONS_TRANSPORT=rabbitmq` состояние брокера показывает `/health` и `notifications:broker-health`.

Вывод команд не содержит email, телефонов, токенов и текстов сообщений; имена каналов, состояний, коды причин и числа допустимы.

### Формат `outbox:status --json`

```json
{"generated_at": "2026-11-05T10:51:05+03:00", "status": "ok", "pending_count": 0,
 "failed_count": 0, "oldest_pending_at": null, "oldest_pending_age_seconds": null,
 "publish_lag_seconds": 0, "published_last_hour": 128,
 "thresholds": {"max_lag_seconds": 60, "max_failed": 0}}
```

Поля стабильны: мониторинг ориентируется на `status` (`ok` или `degraded`), `oldest_pending_age_seconds` и код возврата. `pending_count` — все строки без `published_at`, `failed_count` — те из них, у которых `attempts >= publish_max_attempts`; лаг публикации — возраст старейшей неопубликованной строки. При ошибке выводится `{"generated_at", "status": "error", "error"}` и код 2.

## Расписание

| Задача | Частота | Источник |
|---|---|---|
| `outbox:publish` с описанием `events:publish-outbox` | интервал из `config('events.publish_interval_seconds')` (по умолчанию 5 с) | `routes/console.php`, `App\Console\Scheduling\OutboxPublishFrequency` |
| `notifications:consume-status --once` | интервал из `config('events.status_consume_interval_seconds')` (по умолчанию 60 с) | `routes/console.php` |
| `processed-messages:purge` | ежедневно | `routes/console.php` |
| `orders:purge-idempotency-keys` | каждый час | `routes/console.php` (этап M4) |

Расписание сервиса (`notifications-scheduler`) собирается в `services/notifications/routes/console.php`: `notifications:send --once` раз в минуту, публикатор Outbox с интервалом `outbox.publish_interval_seconds`, `notifications:purge`, `notifications:dlq-purge` и `notifications:telegram:purge` по cron `retention.purge_cron`, снимок gauge `notifications:metrics-snapshot` по `metrics.snapshot_cron` (по умолчанию раз в минуту). Все задачи идут с `withoutOverlapping()`, частоты — только из конфигурации. Процесс бота Telegram (`notifications-telegram`) работает отдельным долгоживущим процессом под профилем compose `telegram`.
`OutboxPublishFrequency` переводит интервал в частоту Laravel: подминутные частоты ограничены 1, 2, 5, 10, 15, 20 и 30 секундами, остальные округляются вверх до ближайшей поддерживаемой (31–59 — до минуты); от 60 секунд включается cron «каждые N минут» с округлением вверх; больше 59 минут — ежечасный запуск. Подминутный повтор работает благодаря `schedule:work`/`schedule:run`; литерала интервала в расписании нет.

## Наблюдаемость

`App\Http\Middleware\RequestId` зарегистрирован глобально в `bootstrap/app.php` и добавляет заголовок `X-Request-Id` на любой ответ, включая 404 до маршрутизации и 500. Внешний идентификатор принимается только по шаблону `[A-Za-z0-9._-]{8,128}`, иначе генерируется UUID: произвольная строка клиента в журнал не попадает. Идентификатор кладётся в атрибуты запроса и лог-контекст `request_id`; уже добавленный контекст не затирается. Потребитель сервиса добавляет в контекст `event_id` и `event_type`, поллер отправки — `notification_id` и `event_id`, канал Telegram — `retry_after` и `fallback_from`; белый список полей задан `App\Logging\TechnicalLogFormatter`. Логи публикатора, шины, сервиса и каналов содержат только идентификаторы, коды причин и классы исключений; payload, `chat_id`, адреса, токены, deep-link и тексты не пишутся.

## Ограничения этапа и что вынесено дальше

- **Horizon и Pulse не подключены**, сборщика метрик и профиля `metrics` в compose нет: `/metrics` читается напрямую с сервисным токеном. В CI (`.github/workflows/ci.yml`) задания `quality`, `assets`, `transport-parity`: последнее гоняет `TransportParity` для сервиса и монолита против RabbitMQ (`broker`) и Redis; без `broker` RabbitMQ-кейсы пропускаются.
- **Транспорт по умолчанию — Redis Streams**, RabbitMQ — опция (`EVENTS_TRANSPORT=rabbitmq`, `NOTIFICATIONS_TRANSPORT=rabbitmq`, профиль `broker`, нужен `ext-sockets`); лаг и pending читают Redis Streams независимо от транспорта, состояние брокера — `/health` и `notifications:broker-health`.
- **Срок хранения отозванных device-токенов** задан (`device_tokens.retention_days`, `NOTIFICATIONS_DEVICE_TOKEN_RETENTION_DAYS`), команды очистки нет; опубликованные строки Outbox не очищаются; тип `order.closed` не введён.
- **Push по умолчанию `fake`** (`NOTIFICATIONS_PUSH_PROVIDER=fcm` требует кредов); языки — `locales.supported` (по умолчанию `ru`), замена — `locales.fallback`; один бот на окружение.
