# Кабинет отправителя: план выполнения

Артефакт запроса кабинета отправителя: текст запроса, `EXPLAIN (ANALYZE, BUFFERS)`, используемый существующий индекс и вывод «новый индекс не нужен». Условия замеров и оговорки — в [README.md](README.md), отчётный запрос — в [Отчёт-по-заказам.md](Отчёт-по-заказам.md), схема и индексы — в [../02-Схема-данных.md](../02-Схема-данных.md).

Набор: 100 000 заказов, 50 отправителей (по 2 000 заказов на каждого), `seed` 42, PostgreSQL 16.15 (замеры сняты до перехода на 18), JIT выключен. План снимается по отправителю `bench-sender-1@benchmark.local`.

## Запрос

Кабинет отправителя — последние заказы одного отправителя:

```sql
SELECT * FROM delivery_orders
WHERE sender_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20
```

Текст совпадает с тем, что выполняет `App\Services\Order\OrderListQuery`: базовый запрос без фильтров тот же, а фильтры списка добавляют `status IN (...)` и границы `created_at` — это те же условия отбора, что и раньше в контроллере.

## EXPLAIN

Планы из `candidate-base.txt` (до миграции отчётных индексов) и `after.txt` (после): используется один и тот же существующий индекс.

До:

```
Limit  (cost=5234.73..5234.78 rows=20 width=257) (actual time=6.481..6.485 rows=20 loops=1)
  Buffers: shared hit=2013
  ->  Sort  (Sort Key: created_at DESC, id DESC, top-N heapsort)
        ->  Bitmap Heap Scan on delivery_orders
              Recheck Cond: (sender_id = ...)
              ->  Bitmap Index Scan on delivery_orders_sender_created_index
```

`Execution Time: 6.595 ms`, buffers 2 013.

После:

```
Limit  (cost=4368.91..4368.96 rows=20 width=256) (actual time=2.452..2.454 rows=20 loops=1)
  Buffers: shared hit=2003
  ->  Sort  (Sort Key: created_at DESC, id DESC, top-N heapsort  Memory: 45kB) (actual time=2.451..2.452 rows=20 loops=1)
        ->  Bitmap Heap Scan on delivery_orders  (actual time=0.481..1.827 rows=2000 loops=1)
              Recheck Cond: (sender_id = '6499'::bigint)
              Heap Blocks: exact=2000
              ->  Bitmap Index Scan on delivery_orders_sender_created_index  (cost=0.00..54.11 rows=1843 width=0) (actual time=0.262..0.263 rows=2000 loops=1)
                    Index Cond: (sender_id = '6499'::bigint)
                    Buffers: shared hit=3
```

`Planning Time: 0.092 ms`, `Execution Time: 2.514 ms`, buffers 2 003.

Разница времени между «до» и «после» относится к пересозданному набору, а не к индексам: состав индексов у этого запроса не меняется, число прочитанных страниц практически то же — 2 013 против 2 003.

## Используемый индекс

| Индекс | Определение | Роль в плане |
|---|---|---|
| `delivery_orders_sender_created_index` | `(sender_id, created_at DESC)`, создан миграцией таблицы заказов (M4) | отбор по равенству `sender_id` (2 000 строк на отправителя); порядок `created_at DESC, id DESC` добирается `top-N heapsort` в 45 кБ |

## Вывод

Новый индекс для кабинета отправителя не нужен. Существующий `delivery_orders_sender_created_index` выбран планировщиком, отбор даёт 2 000 строк на отправителя, а `LIMIT 20` ограничивает сортировку. Кандидаты в миграцию не добавлялись: замер не показал узкого места, которое стоило бы отдельного индекса.
