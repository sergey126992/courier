# Отчёт по заказам: планы выполнения и индексы

Артефакт запроса `GET /api/v1/reports/orders`: текст, `EXPLAIN (ANALYZE, BUFFERS)` до и после, два индекса с обоснованием, метрики времени и `buffers`, вывод. Оговорки — в [README.md](README.md), модуль — [../10-Отчёты.md](../10-Отчёты.md), решение — [ADR-0010](../adr/ADR-0010-доказательная-оптимизация-отчётов.md).

Набор: 100 000 заказов, 200 курьеров, 100 000 назначений, 2 000 смен, `seed` 42, период 30 дней, PostgreSQL 16.15 (замеры сняты до перехода на 18), JIT выключен.

## Запрос

Сводный агрегат — один `WITH`-запрос (`OrderReportQuery`): три строки по типам транспорта с итогами, долями, местами и валютами.

| CTE | Что читает |
|---|---|
| `params` | границы периода (`CAST(? AS timestamptz)`) |
| `types` | доменный список типов через `unnest(...) WITH ORDINALITY` |
| `delivered_assignments` | `assignments` со `status = 'delivered'` и `delivered_at` в периоде |
| `delivered_orders` | `DISTINCT` заказы, соединённые с вручениями периода |
| `created` | `delivery_orders` по `requested_at` в периоде, `COUNT(*)` и `SUM(eta_minutes)` по типу |
| `delivered` | `COUNT(*)` и `SUM(price_amount)` по `delivered_orders` с группировкой по типу |
| `cancelled` | `delivery_orders` по `cancelled_at` в периоде |
| `couriers` | `COUNT(DISTINCT courier_id)` по вручениям периода |
| `currencies` | различные `price_currency` заказов, созданных или вручённых в периоде |

Итоги, доли и места — оконными функциями в том же запросе:

```sql
ROUND(COALESCE(d.revenue, 0) * 100.0 / NULLIF(SUM(COALESCE(d.revenue, 0)) OVER (), 0), 2) AS share_percent,
RANK() OVER (ORDER BY COALESCE(d.revenue, 0) DESC) AS "rank",
SUM(COALESCE(c.orders_created, 0)) OVER () AS total_orders_created,
SUM(COALESCE(c.eta_minutes_total, 0)) OVER () AS total_eta_minutes,
SUM(COALESCE(d.orders_delivered, 0)) OVER () AS total_orders_delivered,
SUM(COALESCE(d.revenue, 0)) OVER () AS total_revenue
```

Секунды смен (`CourierLoadQuery`): `SUM(GREATEST(EXTRACT(EPOCH FROM (least(coalesce(ended_at, to), to) - greatest(started_at, from))), 0))` по `courier_shifts`, пересекающимся с периодом; результат — скаляр и три строки, чтение не зависит от объёма заказов.

## EXPLAIN до

Источник — `candidate-base.txt`, стадия без индексов: оба отбора — полным обходом:

```
Sort  (cost=505114.11..505114.12 rows=3 width=304) (actual time=272.307..272.331 rows=3 loops=1)
  Buffers: shared hit=40034 read=6044
  ...
  CTE delivered_assignments
    ->  Nested Loop  (cost=0.00..3719.51 rows=5515 width=16) (actual time=0.026..18.156 rows=50000 loops=1)
          ->  Seq Scan on assignments a  (cost=0.00..2975.00 rows=49633 width=24) (actual time=0.021..11.230 rows=50000 loops=1)
                Filter: ((status)::text = 'delivered'::text)
                Rows Removed by Filter: 50000
                Buffers: shared hit=1725
  ...
  ->  Seq Scan on delivery_orders o  (cost=0.00..8402.00 rows=100000 width=21) (actual time=1.308..16.655 rows=100000 loops=1)
```

`Execution Time: 276.010 ms`; пять полных обходов: один по `assignments` и четыре по `delivery_orders` (созданные, отмены, валюты, соединение с вручениями).

## Добавленные индексы

| Индекс | Определение | Почему такой тип |
|---|---|---|
| `delivery_orders_requested_at_brin_index` | `USING brin (requested_at)` | сводный запрос дважды отбирает `delivery_orders` по диапазону `requested_at`; таблица растёт по времени, поэтому BRIN даёт диапазонный отбор при минимальном размере индекса и дешёвой записи — в отличие от btree по тому же столбцу |
| `assignments_delivered_at_partial_index` | `(delivered_at) WHERE status = 'delivered'` | в `assignments` не было индекса по `delivered_at`; отчёту нужны только строка со `status = 'delivered'`, поэтому частичный btree хранит половину строк и не обслуживает остальные статусы |

Миграция `2026_11_05_120001_add_reporting_indexes.php` создаёт оба индекса; `down()` снимает ровно их (проверяется тестом миграции).

## EXPLAIN после

Источник — `after.txt`, после применения миграции:

```
Sort  (cost=491594.83..491594.84 rows=3 width=304) (actual time=185.414..185.431 rows=3 loops=1)
  Buffers: shared hit=25993
  ...
  ->  Bitmap Index Scan on assignments_delivered_at_partial_index  (cost=0.00..115.81 rows=5552 width=0) (actual time=1.594..1.595 rows=50000 loops=1)
        Index Cond: ((delivered_at >= p_1.period_from) AND (delivered_at < p_1.period_to))
        Buffers: shared hit=128
  ...
  ->  Bitmap Index Scan on delivery_orders_requested_at_brin_index  (cost=0.00..12.22 rows=12069 width=0) (actual time=0.043..0.043 rows=27940 loops=1)
        Index Cond: ((requested_at >= p.period_from) AND (requested_at < p.period_to))
        Buffers: shared hit=2
```

`Execution Time: 188.008 ms`, `Planning Time: 0.620 ms`.

Что изменилось:

- вручения периода читаются частичным индексом — 128 buffers вместо 1725 у полного обхода `assignments`;
- отбор по `requested_at` идёт через BRIN — 2 buffers на индексное сканирование 27 940 строк;
- три полных обхода `delivery_orders` остаются: отмены (`cancelled_at IS NOT NULL` — индекса нет), валюты (`OR EXISTS` не даёт индексного отбора), соединение с вручениями (`DISTINCT`).

## Метрики

### Серия на одном наборе

Источники — `timed-base.txt`, `timed-brin.txt`, `timed-partial.txt`, `timed-both.txt`; все стадии на одном наборе.

| Стадия | Прогонов | Median, мс | Buffers |
|---|---|---|---|
| без индексов (`base`) | 30 | 189.512 | 33 066 |
| только BRIN (`brin`) | 10 | 176.492 | 14 114 |
| только частичный btree (`partial`) | 10 | 174.726 | 15 721 |
| оба индекса (`both`) | 30 | 179.848 | 24 517 |

Чтение таблицы: `base` → `both` — median 189.512 → 179.848 мс, buffers 33 066 → 24 517 (−26 %). BRIN — 14 114 buffers, частичный btree — 15 721 (стадии по 10 прогонов). Разница median между `brin`, `partial` и `both` — в пределах разброса стенда, поэтому вывод по buffers.

### Полные прогоны команды

| Артефакт | Набор | Прогонов | p50, мс | p95, мс | min, мс | max, мс |
|---|---|---|---|---|---|---|
| `before.txt` (до миграции, с остатками `bench_*`) | 100 000, seed 42 | 100 | 132.573 | 159.139 | 112.571 | 200.127 |
| `after-run1.txt` (после миграции) | 100 000, seed 42 | 100 | 135.022 | 159.540 | 114.386 | 250.717 |
| `after.txt` (после миграции) | 100 000, seed 42 | 100 | 138.498 | 166.609 | 118.559 | 263.026 |

Это разные пересозданные наборы: p50 и p95 не вычитаются. p95 — 159–167 мс при требовании «не выше 300 мс»; каждый артефакт фиксирует `sql_queries = 2`.

## Отклонённые кандидаты

| Кандидат | Что показал план | Решение |
|---|---|---|
| `(transport_type, requested_at)` | планировщик индекс не выбрал: в плане снова четыре `Seq Scan on delivery_orders`, `Execution Time 240.278 ms`, buffers 44 642 + 1 436 | отклонён: пользы нет |
| `(courier_id, delivered_at)` | индекс не выбран, `Execution Time 363.656 ms`, buffers 43 362 + 2 716 — худший результат серии | отклонён: пользы нет |
| `courier_shifts (started_at, ended_at)` | индекс выбран (`Index Only Scan`, 0.356 мс, 4 buffers против 0.855 мс и 19 buffers у полного обхода), но выигрыш — около половины миллисекунды на фоне ~190 мс отчёта | отклонён: выигрыш не оправдывает поддержку индекса при каждой записи смены |
| btree по `delivery_orders(requested_at)` вместо BRIN | не замерялся отдельным артефактом; BRIN выбран как более дешёвый по размеру и записи для колонки, растущей по времени | решение — в [ADR-0010](../adr/ADR-0010-доказательная-оптимизация-отчётов.md) |

## Вывод

Индексы добавлены: планировщик их выбирает, чтение страниц падает — buffers с 33 066 до 24 517, при одиночном BRIN до 14 114; p95 отчёта на 100 000 заказов — 159–167 мс при пределе 300 мс.

Индексы по `(transport_type, requested_at)`, `(courier_id, delivered_at)`, `(started_at, ended_at)` в миграцию не попали: первые два планировщик не выбирает, третий даёт доли миллисекунды; разрез по типам считается по трём строкам агрегата.
