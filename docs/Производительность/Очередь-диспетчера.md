# Очередь диспетчера: план выполнения

Артефакт запроса очереди диспетчера: текст запроса, `EXPLAIN (ANALYZE, BUFFERS)`, используемый существующий индекс и вывод «новый индекс не нужен». Условия замеров и оговорки — в [README.md](README.md), отчётный запрос — в [Отчёт-по-заказам.md](Отчёт-по-заказам.md), схема и индексы — в [../02-Схема-данных.md](../02-Схема-данных.md).

Набор: 100 000 заказов, `seed` 42, PostgreSQL 16.15, JIT выключен.

## Запрос

Очередь диспетчера — список заказов в статусе «создан» от новых к старым:

```sql
SELECT * FROM delivery_orders
WHERE status = 'created'
ORDER BY created_at DESC, id DESC
LIMIT 50
```

Query-объект `App\Services\Dispatch\DispatcherQueueQuery` собирает тот же запрос: статус передаётся единственным биндингом через `status IN (?)`, и PostgreSQL при планировании упрощает его до равенства `status = 'created'`, поэтому план ниже относится к выполняемому коду. Фильтры зоны, периода и транспорта добавляют условия `zone_id = ?`, `created_at` и `transport_type = ?` перед сортировкой; базовая выборка очереди от них не меняется.

## EXPLAIN

Планы из `candidate-base.txt` (до миграции отчётных индексов) и `after.txt` (после) — индекс один и тот же, отчётная миграция его не касается.

До:

```
Limit  (cost=11493.85..11493.98 rows=50 width=257) (actual time=16.396..16.403 rows=50 loops=1)
  Buffers: shared hit=3718
  ->  Sort  (Sort Key: created_at DESC, id DESC, top-N heapsort)
        ->  Bitmap Heap Scan on delivery_orders
              ->  Bitmap Index Scan on delivery_orders_status_created_index
```

`Execution Time: 16.521 ms`, buffers 3 718.

После:

```
Limit  (cost=8365.24..8365.37 rows=50 width=256) (actual time=7.688..7.695 rows=50 loops=1)
  Buffers: shared hit=3706 read=3
  ->  Sort  (Sort Key: created_at DESC, id DESC, top-N heapsort  Memory: 76kB) (actual time=7.687..7.690 rows=50 loops=1)
        ->  Bitmap Heap Scan on delivery_orders  (actual time=0.964..4.449 rows=8556 loops=1)
              Recheck Cond: ((status)::text = 'created'::text)
              Heap Blocks: exact=3700
              ->  Bitmap Index Scan on delivery_orders_status_created_index  (cost=204.51 rows=8563) (actual time=0.599..0.600 rows=8556 loops=1)
                    Index Cond: ((status)::text = 'created'::text)
```

`Planning Time: 0.371 ms`, `Execution Time: 7.793 ms`, buffers 3 706 (hit) + 3 (read).

Разница времени между «до» и «после» относится к пересозданному набору и к прогреву страниц, а не к индексам: набор индексов очереди не меняется. Число прочитанных страниц практически одинаково — 3 718 против 3 709.

## Используемый индекс

| Индекс | Определение | Роль в плане |
|---|---|---|
| `delivery_orders_status_created_index` | `(status, created_at DESC)`, создан миграцией таблицы заказов (M4) | отбор по равенству `status = 'created'`; порядок `created_at DESC, id DESC` добирается `top-N heapsort` по 8 556 отобранным строкам |

Индекс покрывает равенство по статусу и первый ключ сортировки. Второй ключ (`id DESC`) в индексе отсутствует, поэтому план сортирует отобранную пачку, а не читает индекс в готовом порядке: `LIMIT 50` и `top-N heapsort` делают эту сортировку дешёвой — 76 кБ памяти.

## Вывод

Новый индекс для очереди диспетчера не нужен. Существующий `delivery_orders_status_created_index` выбран планировщиком, число прочитанных страниц мало́ (3 709 buffers), а запрос ограничен `LIMIT 50`. Замена индекса на `(status, created_at DESC, id DESC)` или добавление второго индекса не проверялись отдельным замером и в миграцию не попали: польза не доказана, а требование этапа — добавлять только доказанные индексы.
