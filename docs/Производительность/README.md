# Артефакты производительности

Артефакты замеров M8: планы отчётных запросов «до/после», обоснование индексов и числа, на которые опирается решение. Модуль — [../10-Отчёты.md](../10-Отчёты.md), схема — [../02-Схема-данных.md](../02-Схема-данных.md), решение — [ADR-0010](../adr/ADR-0010-доказательная-оптимизация-отчётов.md).

Принцип: индекс попадает в миграцию только когда план «до/после», время и `buffers` показывают пользу; артефакт без числа не аргумент.

## Структура артефакта

Артефакт одного запроса собирается так (требование FR-RPT-166):

| Шаг | Что фиксируется |
|---|---|
| 1 | текст запроса — тот же, что выполняет приложение |
| 2 | `EXPLAIN (ANALYZE, BUFFERS)` до изменения, с размером набора |
| 3 | предлагаемый индекс и обоснование его типа (BRIN, частичный btree, составной) |
| 4 | `EXPLAIN (ANALYZE, BUFFERS)` после изменения |
| 5 | метрики: прочитанные строки, время, `buffers` — до и после |
| 6 | вывод: индекс добавлен или отклонён, и почему |

Планы снимаются `reporting:benchmark --explain` по тем же текстам SQL, что выполняет отчёт: `OrderReportQuery::sql()`, `CourierLoadQuery::sql()`, запросы очереди диспетчера и кабинета отправителя.

## Как воспроизвести замер

Все команды выполняются в контейнере `app`:

```sh
# замер на наборе по умолчанию (100 000 заказов), планы всех четырёх запросов
docker compose exec app php artisan reporting:benchmark --explain

# то же в JSON: метрики и планы машинно-читаемо
docker compose exec app php artisan reporting:benchmark --orders=100000 --runs=100 --explain --json

# замер с временными кандидатами индексов: они создаются до прогона и снимаются после
docker compose exec app php artisan reporting:benchmark --orders=100000 --runs=100 --explain --with-indexes

# набор остаётся в базе для ручных экспериментов
docker compose exec app php artisan reporting:benchmark --runs=1 --keep
```

- Набор детерминирован: `--seed` входит в `setseed` и разметку строк; одинаковый `--seed` — одинаковый набор.
- Наполнение только в `local` и `testing` (`reporting.benchmark.environments`); иначе отказ до изменений в базе.
- Остатки прошлого набора вычищаются по маркеру `BENCH-` в начале прогона, а по умолчанию набор удаляется в `finally` — заказов, пользователей и зоны не остаётся. Если остатки есть, команда возвращает код 2.
- Кандидаты индексов — по `--with-indexes`, с префиксом `bench_`, удаляются в `finally`: «до» и «после» снимаются на одном наборе.

## Условия замеров

| Условие | Значение |
|---|---|
| PostgreSQL | 16.15 — замеры M8 сняты до перехода на PostgreSQL 18. После перехода на 18.6 p95 отчёта 164–189 мс после прогрева (первый прогон 274 мс — холодный кэш), см. [выгоды обновления](<../../../learning/Обновление стека - что получаем.md>) |
| Набор | 100 000 заказов, 200 курьеров, 100 000 назначений (вручений), 2 000 смен |
| Период отчёта | 30 дней; заказы разложены по более широкому окну генерации |
| `seed` | 42 |
| JIT | выключен (`SET jit = off`) на время замера |
| Статистика | `VACUUM (ANALYZE)` после наполнения; в тестах внутри транзакции — только `ANALYZE` |
| Прогрев | отчёт выполняется один раз до серии замеров |
| Процентили | метод ближайшего ранга |

JIT выключен намеренно: на границе стоимости плана PostgreSQL его включает, и компиляция (сотни миллисекунд) попадает в замер. Сравниваются планы, а не LLVM.

## Оговорки

- **Разброс между пересозданными наборами.** Время отчёта на разных наборах одного размера расходится на десятки миллисекунд — сопоставимо с эффектом индексов. Поэтому вывод опирается на серию `timed-*` на **одном** наборе, и на `buffers`; числа из `before.txt`, `after.txt`, `after-run1.txt` — разные наборы, вычитать их нельзя.
- **`before.txt` — «до миграции», но не «без индексов»**: в плане видны кандидаты `bench_*` от прогона с `--with-indexes`; чистое «до» — в `candidate-base.txt`.
- **Абсолютные значения — стендовые**: числа с локального стенда не переносятся на прод; требование этапа — p95 не выше 300 мс на 100 000 заказов — выполняется с запасом.
- **Данные бенчмарка не остаются**: артефакт описывает замер, а не состояние базы.
- **Кандидаты индексов временные**: `bench_*` — только для замера; в миграцию попадают два индекса, остальные кандидаты отклонены.
