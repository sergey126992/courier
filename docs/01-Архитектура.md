| Провайдеры | `app/Providers` | связывание интерфейсов с реализациями, настройка сервисов контейнера | `AppServiceProvider` собирает набор стратегий расчёта под тегом `pricing.estimate-strategies`, регистрирует `StrategyDeliveryEstimator` как singleton, лимит `pricing-estimate` и право `estimate-delivery`; связывает `ZoneRepository` и `DistanceProvider` (кэширующий декоратор над локальным провайдером), регистрирует политики `ServiceZone` и `DeliveryOrder`, лимит `orders-create`; собирает набор правил подбора под тегом `dispatch.assignment-strategies`, регистрирует политики `CourierShift` и `Assignment`, кэш публичного трекинга с его сбросом по смене статуса и лимиты `dispatch-assign`, `courier-actions`, `courier-points`, `courier-heartbeat`, `tracking-link`, `tracking-public`; связывает `EventBus` с `LocalEventBus`, собирает `OutboxPublisher` из параметров `config/events.php`, регистрирует карту слушателей всех восьми типов и собирает `NotificationPolicy` из `config/notifications.php` |
| Слушатели | `app/Listeners` | подписка на события через `EventListener`, эффект в Inbox | каталога нет: с M12 уведомления обрабатывает сервис, локальный слушатель удалён |
| Джобы | `app/Jobs` | асинхронная работа воркера очереди | каталога нет: отправку уведомлений выполняет поллер сервиса, локальная джоба удалена |
| Команды | `app/Console` | проходы публикатора, разбор необработанных сообщений, очистка по срокам хранения и частота расписания | `Commands\PublishOutbox`, `OutboxStatus`, `OutboxFailed`, `NotificationsFailed`, `NotificationsRetry`, `PurgeNotifications`, `PurgeProcessedMessages`; `Scheduling\OutboxPublishFrequency` — перевод интервала из конфигурации в частоту расписания |

Столбец «Состояние» — наполнение слоёв на M7 с поправками M11–M12; прикладные классы этапа (`RedisStreamEventBus`, `EventStreamRouter`, `NotificationStatusProjector`, `NotificationAdminJournal`, `NotificationPreferencesScreen`, `NotificationServiceClient`) — в разделе «Граница сервиса оповещений».
Правила зависимостей: поток сверху вниз (HTTP → операции → домен и модели), обратного нет; домен не знает о фреймворке, базе и HTTP; контроллер вызывает операцию, а не `DB::` или `Model::query()`; модели без бизнес-правил и вызовов сервисов; сервисы и операции внедряются через контейнер; операции не вызывают шину, а пишут строку в `outbox_messages` в своей транзакции, передачу выполняет публикатор; слушатель пишет строки журнала в транзакции Inbox и ставит джобу после `COMMIT`; конфигурацию читают только сервисы и провайдеры.

## Поток запроса

```
браузер
  → nginx:8080 (docker/nginx/default.conf)
  → php-fpm app:9000 (docker/php/www.conf)
  → public/index.php
  → bootstrap/app.php (withRouting: routes/web.php, commands, health: /up)
  → маршрут
  → контроллер
  → операция / домен
  → ответ
```

Что важно: точка входа — `public/`, веб-сервер отдаёт только её; в контейнере `app` приложение работает через `php-fpm`, своего веб-сервера нет; `nginx` резолвит имя `app` по DNS Docker (`resolver 127.0.0.11`), поэтому перезапуск приложения не даёт закешированного 502; `/up` регистрируется в `bootstrap/app.php` параметром `health` без авторизации; очередь и планировщик — те же контейнеры с командами `queue:work` и `schedule:work`, тяжёлые операции не идут в HTTP-запросе.

## География и заказы (M4)

Цепочка «адрес → зона → расстояние → цена → заказ»: HTTP — `EstimateController`, `OrderController` (зону и расстояние клиент не передаёт); операции — `Pricing\EstimateDelivery`, `Order\CreateOrder` собирают `EstimateInput` через `Pricing\EstimateInputFactory`, определяют зону `ZoneResolver` и расстояние `DistanceProvider`; домен — `ZoneResolver` выбирает зону по правилу «меньшая площадь, затем меньший код», `DeliveryOrder` проверяет переход статуса; модели — заказ, история статусов, ключи идемпотентности, исходящие события; `EnsureIdempotencyKey` проверяет ключ повтора и отдаёт сохранённый ответ; `orders:purge-idempotency-keys` чистит истёкшие ключи каждый час (`routes/console.php`).
Подробности — в [05-Зоны-и-расстояния.md](05-Зоны-и-расстояния.md).

## Диспетчеризация и трекинг (M5–M6)

Цепочка «курьер на смене → назначение → движение»: HTTP — `ShiftController`, `AssignmentController`, `TrackingPointController`, `CourierLocationController`; права — `CourierShiftPolicy`, `AssignmentPolicy`, `DeliveryOrderPolicy`; валидация — формы `Dispatch/*` и `Tracking/*`; операции — `Actions\Dispatch\*` (смена, подбор, назначение, переназначение, действия курьера) и `Actions\Tracking\*` (геоточка, heartbeat, чтение, публичная ссылка и ответ); домен — `Domain\Dispatch` и `Domain\Tracking`; модели — `Dispatch\CourierShift`, `Dispatch\Assignment`, `Tracking\TrackingPoint`, `Tracking\AssignmentLastPosition`, `Tracking\CourierLastPosition` (UTC — трейт `ConvertsTimestampsToUtc`); сервисы — `Dispatch\CandidateFinder`, `Tracking\PublicTrackingCache`; `AppServiceProvider` регистрирует правила подбора тегом, политики, лимиты и сброс кэша по событию смены статуса.
Правила зависимостей те же; отбор кандидатов и остаток идут через `DistanceProvider`, поэтому сбой провайдера даёт пустые метрики и `planned`. Подробности — в [07-Диспетчеризация.md](07-Диспетчеризация.md), [08-Трекинг.md](08-Трекинг.md), [02-Схема-данных.md](02-Схема-данных.md), [ADR-0005](adr/ADR-0005-стратегии-подбора.md), [ADR-0006](adr/ADR-0006-целостность-диспетчеризации.md) и [ADR-0007](adr/ADR-0007-публичный-трекинг.md).

## Асинхронность и уведомления (M7, M12)

Цепочка «операция изменила состояние → участник получил уведомление»: операции (`Order\CreateOrder`, `Order\CancelOrder`, `Dispatch\*`) пишут событие в `outbox_messages` в транзакции изменения, шину не вызывают; `outbox:publish` по расписанию запускает `Services\Events\OutboxPublisher` — пачка под `Cache::lock` и `FOR UPDATE SKIP LOCKED`, конверт `EventEnvelope` через `OutboxEventEnvelopeFactory`, транспорт `EventBus` (`RedisStreamEventBus`, `XADD`; в тестах `LocalEventBus`); сервис оповещений пишет `inbox_messages` и ключ дедупликации, создаёт строки журнала и подтверждает после `COMMIT`, отправляет поллер `notifications:send` по email, push и Telegram, состояния меняет `Services\Notifications\NotificationSender` (enum `Domain\Notifications\NotificationStatus`); терминальный статус уходит в поток `events.notifications`, монолит применяет его проекцией `order_notification_status`; `AppServiceProvider` регистрирует шину, публикатор, клиент служебного API и модель доступа к админ-страницам; матриц каналов в монолите нет.
Правила зависимостей те же: домен событий и каналов не знает о фреймворке, базе и конфигурации, потребитель и каналы сервиса — прикладной слой; домены проверяются arch-тестами. Подробности — в [09-Асинхронность.md](09-Асинхронность.md), [02-Схема-данных.md](02-Схема-данных.md), [14-Тесты.md](14-Тесты.md), [ADR-0008](adr/ADR-0008-публикатор-outbox-и-inbox.md), [ADR-0009](adr/ADR-0009-каналы-уведомлений.md) и [ADR-0016](adr/ADR-0016-предпочтения-и-замещение-каналов.md).

## Граница сервиса оповещений (M11–M13)

Уведомления обслуживает приложение `courier/services/notifications/` — Laravel 13 со своим `composer.json`, миграциями, тестами и конфигурацией. Граница по событию: монолит не знает, как доставляется уведомление, сервис — как устроен заказ ([ADR-0014](adr/ADR-0014-граница-сервиса-оповещений.md), транспорт — [ADR-0015](adr/ADR-0015-транспорт-событий.md)).

| Что | Где | Правило |
|---|---|---|
| приложение | `services/notifications/` | отдельный образ, свой `vendor`, свои миграции и тесты; общий код не импортируется |
| база | `notifications` под ролью `notifications` | общей базы нет; роли отозван `CONNECT` к базе монолита |
| контракты | `contracts/notifications/` | единственный экземпляр JSON Schema; сервис получает каталог монтированием только для чтения |
| служебный API | `/api/v1/**` под сервисным токеном, `/health` открыт, `/metrics` под сервисным токеном | вызывается только из админ-страниц и сборщика метрик, не из HTTP-пути заказа |
| очередь необработанных и токены устройств | `dlq_entries`, `device_tokens` в базе сервиса | разбор один — `dlq_entries`; монолит читает и повторяет только через служебный API |
| отправитель | только сервис оповещений | переходный период M11 (`NOTIFICATIONS_DRIVER`, `DeliveryMode`, локальный путь) удалён в M12 |
| предпочтения и привязки | `notification_preferences`, `telegram_link_tokens`, `channel_bindings` сервиса | монолит не хранит, не кэширует и не вычисляет их: читает и сохраняет через служебный API |

Направление потока событий:

```
монолит ── Outbox ──► EventBus / Redis Streams (events.orders, events.contacts) ──► сервис
сервис  ── Outbox ──► events.notifications ──► монолит (проекция order_notification_status)
монолит ── HTTP служебного API ──► сервис (журнал и повтор, только админ-страницы)
```

Правила границы: HTTP-путь заказа не делает синхронных вызовов — смена статуса пишет строку Outbox, ответ не ждёт доставки, сбой сервиса не ломает заказ; контакты получателя приходят событием `user.contact_changed`, а не доступом к `users`; админ-страницы и экран настроек — единственное место синхронного обращения (при недоступности сервиса страница сообщает об ошибке), их клиент — `App\Services\Notifications\Service\NotificationServiceClient`; локального пути нет: события накапливаются, уведомления ждут восстановления; домен и операции M4–M6 о сервисе не знают.
Экран `/account/notifications` получает предпочтения и статус привязки тем же клиентом, `user_id` берётся из сессии и в свойства Livewire не попадает; роль передаётся параметром `role`, набор «роль → типы событий» задаёт конфигурация сервиса.

## Транспорт событий и наблюдаемость (M13)

Транспорт — стратегия за контрактами `EventBus` (монолит) и `EventStream` (сервис). Ветвлений по транспорту в домене и операциях нет: `EVENTS_TRANSPORT` / `NOTIFICATIONS_TRANSPORT` выбирает адаптер в провайдере, неизвестное значение — ошибка конфигурации при старте.

| Адаптер | Сторона | Роль |
|---|---|---|
| `RedisStreamEventBus` / `RedisEventStream` | монолит и сервис | значение по умолчанию: потоки, consumer group, `ack` после эффекта, повторная выдача pending |
| `RabbitMqEventBus` / `RabbitMqEventStream` | монолит и сервис | опция под профилем compose `broker`: exchange типа `topic`, маршрутизация по домену, `prefetch`, per-message TTL, DLX и очередь DLQ |

Правила границы брокера: очередь потребителя — `<поток>.<группа>`, независимые группы получают копию; `ack` только после COMMIT эффекта; сообщение из DLX возвращается в основной поток (`DeadLetterRedriver`) и разбирается обычными правилами; брокер не источник истины — при недоступности публикатор не ставит `published_at`, повторяет по backoff, `/health` сообщает `degraded`; реализации — `php-amqplib` v3 и расширение `ext-sockets`, которое ставят образы обоих приложений. Паритет транспортов проверяется набором тестов ([ADR-0015](adr/ADR-0015-транспорт-событий.md)).
**DLQ не второй источник истины.** Терминальный отказ фиксируется в `dlq_entries` в той же транзакции, что статус и Outbox-событие; повтор возвращает ту же строку журнала ([ADR-0017](adr/ADR-0017-dlq-и-метрики-сервиса.md)). **Метрики и `degraded`.** `GET /metrics` — Prometheus text 0.0.4 за сервисным токеном, при `metrics.enabled=false` — `404`; счётчики и гистограмма инкрементируются в процессе и сбрасываются в кэш, «дорогие» gauge считает задача расписания, поэтому база не пересчитывается; деградация — код `METRICS_UNAVAILABLE`; `/health` добавляет проверку `broker` только при RabbitMQ и сообщает `degraded`/`503`. **Экран «Сервис оповещений».** `GET /notifications/service` — админ-страница с вкладками DLQ и метрик: только читает состояние через `NotificationServiceClient` (список DLQ и повтор — API сервиса, снимок метрик — `/metrics`, возраст Outbox — `outbox_messages`), доступ — gate `notifications:manage` (роль `admin`).

## Контейнеры окружения

| Сервис | Образ или команда | Назначение |
|---|---|---|
| `app` | образ `courier-app:local`, команда `php-fpm` | PHP 8.5 с кодом приложения |
| `nginx` | `nginx:1.27-alpine`, порт `8080:80` | веб-сервер, единственная точка входа снаружи |
| `pgsql` | `postgres:18-alpine`, healthcheck `pg_isready` | база `courier` и тестовая `courier_testing` |
| `redis` | `redis:7-alpine`, healthcheck `redis-cli ping` | кэш, сессии, очереди |
| `queue` | `php artisan queue:work --tries=3 --timeout=60` | обработка очереди; `retry_after` соединения — 90 с, строго больше таймаута воркера |
| `scheduler` | `php artisan schedule:work` | запуск запланированных задач |
| `mailpit` | `axllent/mailpit`, порты `8025` и `1025` | перехват писем |
| `notifications-app` | образ из `services/notifications/Dockerfile`, порт `8081:8000` | API сервиса оповещений и `/health` |
| `notifications-worker` | `php artisan notifications:consume` | потребитель потоков заказов и контактов |
| `notifications-scheduler` | `php artisan schedule:work` | расписание сервиса: поллер отправки, публикатор Outbox, очистка журнала и токенов |
| `notifications-telegram` | `php artisan notifications:telegram:poll`, профиль compose `telegram` | процесс бота: long polling апдейтов и подтверждение привязки; при выключенном канале не запускается |
| `rabbitmq` | `rabbitmq:3.13-management-alpine`, профиль compose `broker`, порты `5672` и `15672` | опциональный брокер событий: management UI и очереди; без профиля всё работает на Redis |

`app`, `queue` и `scheduler` собираются из одного образа и одного блока `x-app`: код и переменные окружения у них общие, различается только команда. `notifications-app`, `notifications-worker` и `notifications-scheduler` собираются из образа сервиса (`courier-notifications:local`) и монтируют общий каталог схем `contracts/notifications` только для чтения.

## Как проверяются границы

Границы заданы архитектурными тестами `tests/Arch/ArchTest.php` и `tests/Arch/LocalNotificationPathTest.php`, которые запускаются вместе с обычным прогоном:

| Тест | Что проверяет |
|---|---|
| «домен не зависит от фреймворка» | `App\Domain` не использует `Illuminate`, `Laravel`, `Eloquent`, `Http`, `DB` |
| «в коде нет отладочного вывода» | нигде не вызываются `dd`, `dump`, `var_dump`, `ray` |
| «контроллеры не работают с базой напрямую» | `App\Http\Controllers` не использует `DB`, `Model`, `Query\Builder` |
| «не содержит прямых запросов к базе в контроллерах» | в файлах контроллеров нет подстрок `DB::` и `Model::query(` |
| «не обращается к фреймворку, базе и конфигурации в домене событий» | `App\Domain\Events` не использует `Illuminate`, `Laravel`, `Eloquent`, `config` |
| «не обращается к фреймворку, базе и конфигурации в домене уведомлений» | `App\Domain\Notifications` не использует `Illuminate`, `Laravel`, `Eloquent`, `config` |
| «локального отправителя уведомлений больше нет» (`tests/Arch/LocalNotificationPathTest.php`) | нет `app/Jobs`, `app/Listeners`, локальных сервисов отправки, команд, миграций и таблиц журнала; монолит не читает `notifications.driver` и ключи локальной матрицы |
| «экран настроек не дублирует реестр событий» (`tests/Arch/NotificationPreferencesGuardTest.php`) | в монолите нет набора «роль → типы событий» и реестра типов событий для экрана |

Тесты — рабочий предохранитель: файл в домене с `dump()` и `Illuminate` валил прогон, после удаления — снова зелёный.

## Где живёт конфигурация

| Что настраивается | Где |
|---|---|
| Часовой пояс и локаль | `config/app.php` (`APP_TIMEZONE`, `APP_LOCALE`), значения окружения — `Europe/Moscow` и `ru` |
| Подключения к БД, Redis, почте | `config/database.php`, `config/cache.php`, `config/session.php`, `config/mail.php` + переменные окружения |
| Зоны и расстояния | `config/geography.php`: коэффициент удлинения маршрута, TTL кэша, число знаков в ключе, лок (`GEOGRAPHY_DISTANCE_*`) |
| Заказы и идемпотентность | `config/orders.php`: допуск `requested_at`, длина ключа повтора, TTL (`ORDERS_*`) |
| Диспетчеризация | `config/dispatch.php`: правило подбора по умолчанию и предел числа кандидатов (`DISPATCH_*`) |
| Трекинг | `config/tracking.php`: срок публичной ссылки, окно и разброс кэша, допуск времени точки (`TRACKING_*`) |
| Асинхронность | `config/events.php`: транспорт и имена потоков, группа и имя потребителя, размер пачки и задержка повторной выдачи, интервал и размер пачки публикатора, предел попыток, ряд backoff, TTL блокировки, версия контракта, каталог схем, срок хранения Inbox, пороги `outbox:status` и блок `rabbitmq` (подключение, exchange, DLX, TTL, предел попыток, домены маршрутизации) (`EVENTS_*`, `RABBITMQ_*`) |
| Уведомления | `config/notifications.php`: адрес, токен, таймаут, повторы и пауза служебного API сервиса, размер порции админ-журнала (`NOTIFICATIONS_*`); матрицы каналов, предпочтений и канала Telegram здесь нет |
| Сервис оповещений | `services/notifications/config/notifications.php` и `.env` сервиса: транспорт и потоки (включая блок `transport.rabbitmq`), каталог схем, служебный токен, процессы, сроки хранения, пороги `/health`, предпочтения (`preferences`), канал Telegram (`telegram`), а также блоки M13 — `dlq`, `device_tokens`, `metrics` и `push.fcm` (`NOTIFICATIONS_*`, `FCM_*`, `RABBITMQ_*`) |
| Лимиты частоты | `config/rate_limits.php`; именованные лимиты `pricing-estimate`, `orders-create`, `dispatch-assign`, `courier-actions`, `courier-points`, `courier-heartbeat`, `tracking-link` и `tracking-public` собираются в `AppServiceProvider` |
| Переменные для разработки | `.env` (в репозиторий не попадает), образец — `.env.example` без секретов |
| Переменные контейнеров | `docker-compose.yml`, блок `x-app` |
| Настройки PHP и пула php-fpm | `docker/php/app.ini`, `docker/php/www.conf` |
| Окружение тестов | `phpunit.xml`, блоки `<server>` и `<env>` (см. [14-Тесты.md](14-Тесты.md)) |

Код и конфигурация разделены: значения читаются только через `config()`, переменные окружения нигде не используются напрямую.

## Почему домен отделён

Логику домена можно проверить без базы, фреймворка и HTTP — тесты быстрые, без фикстур; домен переносим: смена Laravel, ORM или появление API не затрагивают правила; запрет фасадов не даёт протащить SQL в бизнес-правила (ловит arch-тест); зависимости видны в конструкторах, подмены — обычными фейками.
