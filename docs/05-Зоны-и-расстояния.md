# Зоны обслуживания и расстояния

Этап M3: справочник зон, справочник адресов для подсказок, выбор зоны по координатам, провайдер расстояний с кэшем и расчёт стоимости по адресам. Требования — в [ЧТЗ - География и заказы](<../.github/docs/Техническое задание/География и заказы/ЧТЗ - География и заказы.md>).
Слои — в [01-Архитектура.md](01-Архитектура.md), цена и ETA — в [04-Стоимость-и-ETA.md](04-Стоимость-и-ETA.md), заказы — в [06-Заказы.md](06-Заказы.md).

## Зона обслуживания

Зона — запись справочника, по которой система решает, обслуживается ли адрес.

| Поле | Правила | Хранение |
|---|---|---|
| `code` | 2–16 символов, нижний регистр, цифры и дефисы; уникален без учёта регистра; не меняется | `service_zones.code`, уникальный индекс по `lower(code)` |
| `name` | до 255 символов                                                       | `service_zones.name` |
| `boundary` | прямоугольник или многоугольник в координатах                         | `service_zones.boundary` (jsonb) |
| `base_fee_amount` | целое неотрицательное число в минорных единицах (копейках)            | `service_zones.base_fee_amount` |
| `currency` | три символа, по умолчанию `RUB`                                       | `service_zones.currency` |
| `is_active` | по умолчанию `true`; неактивная зона не участвует в выборе            | `service_zones.is_active` |

Удаления зоны нет: устаревшая деактивируется через `PATCH` (`is_active: false`), `code` неизменяем и в `PATCH` отклоняется валидацией. Изменение базовой ставки не влияет на уже созданные заказы: заказ хранит свою цену.

## Границы и формат координат

Граница — прямоугольник с двумя углами или многоугольник с точками в порядке обхода. Координаты **везде** — `latitude` и `longitude` (адреса, точки границы, ответы API); формы `lat`/`lng` нет. Прямоугольник — юго-западный и северо-восточный углы:

```json
{
  "type": "rectangle",
  "south_west": { "latitude": 55.70, "longitude": 37.50 },
  "north_east": { "latitude": 55.80, "longitude": 37.70 }
}
```

Многоугольник — не меньше трёх точек:

```json
{
  "type": "polygon",
  "points": [
    { "latitude": 55.70, "longitude": 37.50 },
    { "latitude": 55.80, "longitude": 37.50 },
    { "latitude": 55.75, "longitude": 37.70 }
  ]
}
```

Правила проверки: широта от −90 до 90, долгота от −180 до 180, точность — не больше шести знаков после запятой; у прямоугольника северо-восточный угол строго севернее и восточнее юго-западного; у многоугольника точки идут в порядке обхода, вырожденная граница отклоняется; точка на ребре считается попавшей в зону; площадь — в км² по плоской проекции на среднюю широту.
Неверная граница даёт **одно** сообщение по полю `boundary`: сначала проверяется структура (тип, набор точек, диапазоны), затем доменное правило (порядок углов, число точек, вырожденность).

## Выбор зоны при пересечении границ

Зону по координатам определяет `App\Domain\Geography\ZoneResolver`: берутся только активные зоны (`ZoneRepository::active()`), остаются содержащие точку; при пересечении выигрывает зона с **меньшей площадью**, при равенстве — с **меньшим кодом**. Порядок записей в базе на ответ не влияет.
Нет активных зон или точка вне всех — доменное исключение `AddressOutsideServiceArea`, API отвечает `ADDRESS_OUTSIDE_SERVICE_AREA`. Зона определяется только по адресу **забора**; адрес доставки может быть вне зон — расстояние до него считается, радиус проверяет расчёт типа транспорта.

## Справочник адресов

Справочник адресов — внутренняя таблица `address_directory_entries` (`App\Models\Geography\AddressDirectoryEntry`): одна запись — один дом для подсказок формы заказа. Внешние сервисы не вызываются.

| Поле | Правила | Хранение |
|---|---|---|
| `district` | до 255 символов; входит в ключ уникальности без учёта регистра | `address_directory_entries.district` |
| `street` | до 255 символов; по ней идёт поиск подсказок        | `address_directory_entries.street`, индекс `address_directory_entries_street_lower_index` по `lower(street)` |
| `house` | до 64 символов                                       | `address_directory_entries.house` |
| `latitude`, `longitude` | `decimal(9,6)` — шесть знаков после запятой, около 0,1 м; модель отдаёт их строкой (`decimal:6`) | `address_directory_entries.latitude`, `address_directory_entries.longitude` |
| `is_active` | по умолчанию `true`; неактивная запись остаётся в справочнике, но в подсказках не участвует | `address_directory_entries.is_active`, индекс по `is_active` |

Адрес уникален без учёта регистра: индекс `address_directory_entries_address_lower_unique` по `lower(district), lower(street), lower(house)`. С заказом запись не связана: `delivery_orders` хранит свой снимок адреса и координат. Подпись собирает модель: `label()` → «Улица, дом — район».

### Поиск подсказок

`App\Actions\Geography\SearchAddressDirectory::handle()` — единственный источник подсказок: строка обрезается и приводится к нижнему регистру (короче двух символов — пустая выдача без запроса), ищутся только действующие записи (`scopeActive()`) по `street`, `district`, `house` без учёта регистра.
Символы `\`, `%` и `_` экранируются (`lower(column) LIKE ? ESCAPE ?`); порядок — `lower(street)`, `lower(house)`, `id`; не больше восьми подсказок; элемент выдачи — `['id', 'label', 'district', 'street', 'house']`.

### Связь с зонами

Справочник зону не проверяет: зону по координатам определяет `App\Domain\Geography\ZoneResolver` при расчёте и создании заказа, поэтому адрес забора вне зон даёт `ADDRESS_OUTSIDE_SERVICE_AREA`, а адрес доставки вне зон допустим.

### Демо-данные

`Database\Seeders\GeographyDemoSeeder` наполняет справочник идемпотентно и подключён в `DatabaseSeeder` после пользователей: зона `msk-demo` — «Москва (демо)», прямоугольник 55.60–55.90 / 37.40–37.80, базовая ставка 19 900 копеек; 22 адреса — 20 внутри зоны и 2 в Санкт-Петербурге для сценария `ADDRESS_OUTSIDE_SERVICE_AREA`.
Фабрика `Database\Factories\Geography\AddressDirectoryEntryFactory` создаёт неактивную запись (`inactive()`) и адрес точки через `forAddress()`.

### Граница веб-формы и API

В форме «Новый заказ» координаты не вводятся: `pickup` и `dropoff` собираются по идентификатору записи справочника. API не меняется: `POST /api/v1/estimates` и `POST /api/v1/orders` по-прежнему принимают адреса с координатами.

## API зон

Все маршруты требуют токен и доступны только администратору; права проверяет политика `ServiceZonePolicy`.

| Метод | Путь | Назначение | Коды |
|---|---|---|---|
| GET | `/api/v1/zones` | список зон, фильтр `is_active` | 200, 401, 403 |
| POST | `/api/v1/zones` | создание зоны | 201, 401, 403, 422 |
| PATCH | `/api/v1/zones/{zone}` | изменение и деактивация | 200, 401, 403, 404, 422 |

Список — в порядке кода, без пагинации: `{"data": [ ... ]}`; необязательный `is_active` (`1`/`0`) фильтрует активные и неактивные зоны. Создание — 201 с `Location: /api/v1/zones/{id}`. Изменение принимает `name`, `boundary`, `base_fee_amount`, `currency`, `is_active`; поле `code` запрещено. Несуществующая зона — 404, роль без права — 403, ошибка формата или границы — 422. Пример запроса создания:

```json
{
  "code": "msk-center",
  "name": "Центр Москвы",
  "boundary": {
    "type": "rectangle",
    "south_west": { "latitude": 55.60, "longitude": 37.40 },
    "north_east": { "latitude": 55.90, "longitude": 37.80 }
  },
  "base_fee_amount": 19900,
  "currency": "RUB"
}
```

Ответ 201:

```json
{
  "data": {
    "id": 1,
    "code": "msk-center",
    "name": "Центр Москвы",
    "boundary": {
      "type": "rectangle",
      "south_west": { "latitude": 55.6, "longitude": 37.4 },
      "north_east": { "latitude": 55.9, "longitude": 37.8 }
    },
    "base_fee_amount": 19900,
    "currency": "RUB",
    "is_active": true
  }
}
```

Граница в ответе отдаётся в той же форме, которую принимает `PATCH`: ответ можно отправить обратно без преобразований.

## Провайдер расстояний

Контракт домена — `App\Domain\Geography\Contracts\DistanceProvider`:

```php
public function between(Coordinates $from, Coordinates $to): Distance;
```

Домен не знает, как считается расстояние: по прямой, по маршруту или через внешний сервис.

### Локальная реализация

`App\Services\Geography\HaversineDistanceProvider` считает по формуле гаверсинуса (радиус Земли 6371.0088 км) и умножает на коэффициент удлинения маршрута из конфигурации (по умолчанию `1.3`), потому что реальный маршрут длиннее прямой. Результат округляется до сотых километра и возвращается как `Distance`.

### Кэш

`App\Services\Geography\CachedDistanceProvider` — декоратор над провайдером:

| Свойство | Поведение |
|---|---|
| Ключ | `geography:distance:<lat,lon>\|<lat,lon>`; координаты округлены до 3 знаков, разделитель внутри точки — `,`, между точками — `\|` |
| Направление | не влияет: пара координат сортируется, поэтому `A → B` и `B → A` дают один ключ |
| TTL | 3600 с из конфигурации |
| Защита от «промаха стаи» | лок на ключ (`<ключ>:lock`): TTL 10 с, ожидание 5 с; после получения лока кэш перечитывается |
| Истечение лока | обработчик не блокируется: перечитывает кэш и в крайнем случае считает сам |
| Сбой провайдера | исключение не кэшируется — следующий вызов снова обращается к провайдеру |

Настройки — в `config/geography.php`:

| Ключ | По умолчанию | Переменная окружения |
|---|---|---|
| `geography.distance.route_elongation_factor` | `1.3` | `GEOGRAPHY_DISTANCE_ELONGATION` |
| `geography.distance.cache_ttl_seconds` | `3600` | `GEOGRAPHY_DISTANCE_CACHE_TTL` |
| `geography.distance.cache_key_decimals` | `3` | `GEOGRAPHY_DISTANCE_CACHE_DECIMALS` |
| `geography.distance.lock.ttl_seconds` | `10` | `GEOGRAPHY_DISTANCE_LOCK_TTL` |
| `geography.distance.lock.wait_seconds` | `5` | `GEOGRAPHY_DISTANCE_LOCK_WAIT` |
| `geography.distance.timeout_seconds` | `3` | `GEOGRAPHY_DISTANCE_TIMEOUT` |
| `geography.distance.retries` | `2` | `GEOGRAPHY_DISTANCE_RETRIES` |

Таймаут и число повторов адресованы будущему внешнему провайдеру: локальный расчёт их не использует. В `AppServiceProvider` `DistanceProvider` — singleton из кэширующего декоратора над локальным провайдером.

## Расчёт по адресам

`POST /api/v1/estimates` принимает адреса забора и доставки и считает расстояние сам.

| Поле | Обязательность | Правила |
|---|---|---|
| `transport` | обязательно | `on_foot`, `light`, `car` |
| `light_vehicle_kind` | обязательно для `light`, иначе запрещено | `bicycle`, `scooter`, `e_scooter`, `e_bike` |
| `pickup` | обязательно | `district`, `street`, `house`, `latitude`, `longitude`; лишние ключи отклоняются |
| `dropoff` | обязательно | те же поля, что у `pickup` |
| `parcel` | обязательно | **вложенный** объект: `weight_grams`, `dimensions{length,width,height}`, `declared_value{amount,currency}` |
| `requested_at` | необязательно | момент заявки, по умолчанию текущее время приложения |
| `is_paid_parking` | необязательно | признак платной парковки |
| `distance_km` | запрещено | готовое расстояние не принимается |

Порядок работы: адреса → зона по адресу забора → расстояние провайдером → расчёт M2. Ответ — плоский JSON без обёртки `data` (`transport`, `light_vehicle_kind`, `distance_km`, `eta_minutes`, `price`, `breakdown`).
Старые формы запроса дают 422: плоское тело без объекта `parcel` — одно сообщение по полю `parcel`; поле `distance_km` в запросе — сообщение по полю `distance_km`, расстояние определяет сервер.

## Коды ошибок географии

| Код | HTTP | Когда | `details[0].field` |
|---|---|---|---|
| `ADDRESS_OUTSIDE_SERVICE_AREA` | 422 | адрес забора не попал ни в одну активную зону | `pickup` |
| `DISTANCE_PROVIDER_UNAVAILABLE` | 503 | провайдер расстояний не смог определить расстояние | нет деталей |

`ADDRESS_OUTSIDE_SERVICE_AREA` содержит поле `pickup` и пояснение, что не обслужен адрес забора. `DISTANCE_PROVIDER_UNAVAILABLE` не раскрывает причину и адреса: только код, заголовок и «повторите позже». Ошибки по весу и радиусу — в [04-Стоимость-и-ETA.md](04-Стоимость-и-ETA.md).

## Границы этапа

Картографии и маршрутизации нет: расстояние — по прямой с коэффициентом удлинения; внешний провайдер подключается заменой реализации за контрактом `DistanceProvider`. Платные зоны не реализованы: базовая ставка хранится в справочнике, но в расчёте M2 не участвует. Ручного выбора зоны нет — её определяет сервер по адресу забора. Кэш общий (Redis), отдельного хранилища расстояний нет. Административного интерфейса справочника адресов нет: записи заводятся сидером или напрямую в базе.
