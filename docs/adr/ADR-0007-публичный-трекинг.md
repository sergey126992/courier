# ADR-0007. Публичный трекинг

| Поле | Значение |
|---|---|
| Статус | принято |
| Дата | 2026-11 |
| Этап | M6 (трекинг) |
| Требования | FR-TRK-131…138, раздел 4.9 и 8.6 ЧТЗ «Диспетчеризация и трекинг» |
| Связанные документы | [Трекинг](../08-Трекинг.md), [Заказы](../06-Заказы.md), [Схема данных](../02-Схема-данных.md), [ADR-0003](ADR-0003-идемпотентность.md) |

## Контекст

Получателю нужно открыть состояние заказа без регистрации, отправителю — поделиться ссылкой. Публичная страница не должна раскрывать персональные данные, а поток открытий — бить в базу и провайдер расстояний.

Вопросы, которые нужно было решить сразу:

- как выдавать и отзывать доступ: хранить ссылки в таблице или кодировать всё в самой ссылке;
- какой срок жизни выбрать и что произойдёт после его истечения;
- какие поля попадают в публичный ответ;
- как ограничить частоту обращений, если пользователь не аутентифицирован;
- как обновлять публичный ответ, который читается чаще, чем меняется.

Ограничения:

- секрет подписи не попадает в ответы и логи;
- чужой заказ и несуществующий код отвечают одинаково;
- публичный ответ не пересчитывает прогноз заказа;
- ссылка не должна открывать доступ к самому заказу (адресам, цене, истории).

## Решение

- Ссылка — `URL::temporarySignedRoute('tracking.public', ...)`: код трекинга и срок действия, целостность держит подпись приложения. Маршрут закрыт middleware `signed`, обращения — лимитом по IP.
- Отдельной таблицы ссылок нет. Код и срок читаются из URL, база для проверки ссылки не нужна.
- Срок жизни — `tracking.link_ttl_hours` (`TRACKING_LINK_TTL_HOURS`), по умолчанию 168 часов (7 суток). Повторный запрос отдаёт новую ссылку с новым сроком; отзыва нет.
- Создать ссылку может владелец заказа или диспетчер — те же права, что у чтения трекинга; чужой заказ даёт 404.
- Публичный ответ — белый список: `status`, `status_label`, `eta_minutes`, `eta_at`, `district`, `updated_at`. Адреса, координаты, имя, телефон, цена, номер заказа и код трекинга не попадают по построению: снимок из скаляров без модели заказа.
- Ответ кэшируется по ключу `tracking:public:{code}` на 10 секунд с разбросом ±20 %; смена статуса заказа удаляет ключ через событие модели `DeliveryOrder::updated`.

## Альтернативы и причины отказа

| Альтернатива | Почему отказались |
|---|---|
| Таблица ссылок с токеном, сроком и отзывом | Появляются миграция, уборка просроченных строк и запрос к базе на каждое открытие. Отзыв ссылки не требуется требованиями, а stateless-ссылка даёт тот же доступ без состояния |
| JWT в качестве токена ссылки | Требует библиотеки, ротации ключей и собственной проверки подписи; `temporarySignedRoute` и middleware `signed` уже используются для подтверждения почты и сброса пароля |
| Публичный доступ по `tracking_code` без подписи | Код короткий и перебираемый; постоянная угадываемая ссылка не имеет срока и не может быть закрыта. Подпись и срок — минимальная защита |
| Сессия или отдельный гостевой токен | Получатель не аутентифицирован и не должен регистрироваться; выпуск токенов ради одной страницы усложняет контракт |
| Полный ресурс заказа с фильтрацией на клиенте | Белый список на сервере надёжнее: добавление поля в модель заказа не попадает в публичный ответ автоматически |
| Пересчёт остатка ETA в публичном ответе | Требует позиции курьера и вызова провайдера расстояний на каждое открытие; ЧТЗ фиксирует, что публичный ответ показывает зафиксированный прогноз |
| Долгий кэш (минуты) | Пользователь увидел бы устаревший статус после вручения; короткое окно с jitter защищает от одновременных открытий и почти не влияет на актуальность |

## Последствия и цена

Плюсы:

- нет таблицы ссылок, миграций и уборки: проверка ссылки не обращается к базе;
- публичный ответ не содержит персональных данных по построению, а не по фильтрации;
- повторные открытия в окне кэша не обращаются к базе и не считают ETA;
- смена статуса сбрасывает кэш из одного места: действия назначения, забора, вручения и отмены о кэше не знают.

Цена и риски:

- выданную ссылку нельзя отозвать: компрометация URL равносильна доступу к публичному ответу на 168 часов;
- код трекинга виден в URL, журналах прокси и истории браузера — принято осознанно: за ним стоит ограниченный публичный ответ;
- подпись опирается на `APP_KEY`: его смена обесценивает выданные ссылки, а расхождение часов между узлами ломает проверку срока;
- срок жизни проверяется на стороне приложения; при длинной цепочке прокси расхождение времени может давать 403 раньше или позже ожидаемого;
- лимит по IP обходится сменой адреса или общим NAT: для локального контура приемлемо, для продакшена нужен иной контур защиты;
- кэш живёт секунды, поэтому сразу после смены статуса возможен ответ со старым статусом при пропущенном сбросе;
- отзыв доступа потребует таблицы ссылок или версии кода — изменение контракта, а не настройка.
