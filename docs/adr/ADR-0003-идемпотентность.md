# ADR-0003. Идемпотентность создания заказа

| Поле | Значение |
|---|---|
| Статус | принято |
| Дата | 2026-11 |
| Этап | M4 (заказы) |
| Требования | FR-ORD-108…112, раздел 8.2 ЧТЗ «География и заказы» |
| Связанные документы | [Заказы](../06-Заказы.md), [ADR-0004](ADR-0004-целостность-заказов.md), [Архитектура](../01-Архитектура.md) |

## Контекст

Создание заказа — неидемпотентная операция с побочными эффектами: запись в `delivery_orders`, первая запись истории, событие в Outbox, расход номера из последовательности. Клиент повторяет запрос по обычным причинам: таймаут, обрыв соединения, повторная отправка формы, автоматический retry. Без защиты каждый повтор создаёт второй заказ и номер, а отличить намеренный второй заказ от повтора нельзя.

Ограничения, которые определили решение:

- требование фиксирует заголовок `Idempotency-Key` и проверку ключа **до** вызова операции;
- повтор с тем же ключом и телом обязан вернуть тот же ответ, а не просто «не создавать заказ»;
- ключ уникален в пределах пользователя: разные отправители могут использовать одинаковые значения;
- срок хранения ключей ограничен и задаётся конфигурацией, старые записи не должны копиться;
- справочник заказов и его нумерация остаются серверными: номер `CRG-ГГГГ-NNNNNN` выдаёт последовательность.

## Решение

- Обязательный заголовок `Idempotency-Key` (16–64 символа); его проверяет промежуточный слой `EnsureIdempotencyKey` на маршруте создания заказа.
- Таблица `idempotency_keys` с уникальным индексом `(user_id, key)`; запись хранит отпечаток тела, состояние, сохранённый ответ и `expires_at`.
- Отпечаток тела — SHA-256 канонического JSON (ключи отсортированы), поэтому порядок полей не влияет на сравнение.
- Состояния: `in_progress` (запрос выполняется) и `completed` (ответ сохранён). Ключ занимает вставка записи: конфликт уникальности означает, что ключ занят.
- Повтор: при совпадении отпечатка и `completed` отдаётся сохранённый код и тело без выполнения операции; другой отпечаток — `IDEMPOTENCY_KEY_CONFLICT` (422), незавершённая запись — `IDEMPOTENCY_KEY_IN_PROGRESS` (409).
- Неуспешный ответ и исключение удаляют запись: клиент может повторить запрос с тем же ключом.
- Срок хранения — 24 часа; просроченная запись считается отсутствующей. Чистка — команда `orders:purge-idempotency-keys`, запускаемая планировщиком каждый час.

## Альтернативы и причины отказа

| Альтернатива | Почему отказались |
|---|---|
| Проверка дублей по полям заказа (адреса, посылка, транспорт, время) | Нет естественного уникального ключа: два законных одинаковых заказа от одного отправителя возможны, и запретить их нельзя. Сравнение по нескольким jsonb-полям дорого, а «окно» поиска дубля (например, минута) делает поведение недетерминированным: результат зависит от нагрузки и часов |
| Уникальный индекс по хешу тела | Блокирует не повторы, а законные одинаковые заказы — навсегда, если индекс глобальный, или на период, если он составной по дате. Кроме того, хеш не даёт вернуть тот же ответ: пришлось бы всё равно хранить тело ответа и добавлять ту же таблицу. Хеш по телу также ломается при любом изменении набора полей запроса |
| Клиентский UUID как первичный ключ заказа | Идентификатор заказа становится клиентским, а номер `CRG-ГГГГ-NNNNNN` по-прежнему выдаёт сервер: появляются два идентификатора и их отображение. Клиент может прислать чужой или уже использованный UUID, а мошеннический повтор с тем же UUID и другим телом ничем не отличается от честного. Проверка тела всё равно нужна — то есть нужна и таблица ключей |
| Хранить ключ только в кэше (Redis) | Кэш не даёт атомарной уникальности на паре «пользователь + ключ» и может быть вытеснен или очищен, после чего повтор создаст второй заказ. Сохранённый ответ тоже пришлось бы держать вне кэша |

## Почему промежуточный слой, а не операция

- Ключ проверяется до вызова операции: слой отдаёт сохранённый ответ, не заходя в `CreateOrder`, поэтому повтор не тратит номер, не считает цену и не пишет событие.
- Запись «выполняется» живёт ровно столько, сколько операция: создаётся до вызова и удаляется при ошибке, без таймеров и фоновой очистки.
- Операция создания остаётся про заказ: порядок «зона → расстояние → расчёт → транзакция» не смешивается с транспортом ключа и форматом ответа.
- Правило переиспользуемо: тот же слой подключается к другому маршруту заголовком, без правки операции.

## Последствия и цена

Плюсы:

- повтор безопасен: второй заказ не создаётся, ответ идентичен первому;
- конфликт тела виден клиенту отдельным кодом, а не молчаливым дублем;
- нет эвристик «похожих заказов»: решение принимается по явному ключу;
- ключи не копятся: срок хранения и ежечасная очистка.

Цена:

- дополнительная таблица и запись на каждый успешный запрос создания;
- нужна команда очистки и её запуск по расписанию, иначе таблица растёт;
- повтор не возвращает заголовок `Location`: сохранены только код и тело, поэтому ссылку на заказ клиент получает лишь из первого ответа;
- клиент обязан различать `IDEMPOTENCY_KEY_IN_PROGRESS` (409, можно повторить позже) и `IDEMPOTENCY_KEY_CONFLICT` (422, тело другое);
- сохранённое тело — копия ответа: при смене формата ответа старые записи отдают прежнюю форму;
- отпечаток считается по телу запроса без учёта маршрута и заголовков: слой рассчитан на один эндпоинт, а не на общий ключ для разных операций.

## Что решение не покрывает

- Идемпотентность отмены и других операций: ключ подключён только к созданию заказа.
- Автоматические повторы внутри приложения, повторная обработка очереди и публикация событий — этап M7.
- Привязку ключа к версии API и к набору заголовков запроса.
- После аварийного завершения процесса запись остаётся `in_progress` до `expires_at`, и повтор до этого момента получает 409.
