# ADR-0014. Граница сервиса оповещений

| Поле | Значение |
|---|---|
| Статус | принято |
| Дата | 2026-11 |
| Этап | M11 (сервис оповещений) |
| Требования | FR-NTF-201…216, FR-NTF-231…236, FR-NTF-291…300, разделы 4–7 ЧТЗ «Сервис оповещений» |
| Связанные документы | [Асинхронность и уведомления](../09-Асинхронность.md), [Схема данных](../02-Схема-данных.md), [Архитектура](../01-Архитектура.md), [README сервиса оповещений](../../services/notifications/README.md), [ADR-0015](ADR-0015-транспорт-событий.md), [ADR-0009](ADR-0009-каналы-уведомлений.md) |

> **Актуальность.** Решение о переходном периоде и двух режимах доставки отменено в M12: локальный путь, `NOTIFICATIONS_DRIVER` и `DeliveryMode` удалены, отправитель один — сервис. Предпочтения получателя и замещение каналов — [ADR-0016](ADR-0016-предпочтения-и-замещение-каналов.md); фактическое состояние — в [09-Асинхронность.md](../09-Асинхронность.md).

## Контекст

На M7 уведомления жили в монолите: слушатель `SendOrderNotifications` создавал строки журнала, джоба `SendNotification` отправляла письмо или push, матрица каналов лежала в `config/notifications.php`. Для одного приложения этого достаточно, для развития слоя — нет:

- правила каналов, тексты и шаблоны должны меняться без релиза монолита;
- журнал отправок растёт независимо от заказов и должен жить в своей базе со своими сроками хранения;
- персональные данные (email получателя) нельзя класть в события заказа, в журналы и в тексты;
- сбой отправки не должен влиять на создание заказа и смену статуса;
- источник истины по предпочтениям и контактам получателя — будущий сервис, а не таблицы монолита;
- переходный период неизбежен: локальный путь M7 работает, его нельзя удалить одномоментно.

## Решение

**Отдельное приложение.** Сервис — `courier/services/notifications/`: Laravel 12 со своим `composer.json`, `Dockerfile`, миграциями, тестами и конфигурацией. Контейнеры `notifications-app` (API и `/health`, порт 8081), `notifications-worker` (потребитель потоков), `notifications-scheduler` (поллер отправки, публикатор Outbox, очистка) перезапускаются независимо от монолита.

**Своя база и роль.** База и роль `notifications` создаются init-скриптом `docker/pgsql/init/02-create-notifications-db.sql`; роли отозван `CONNECT` к базе монолита, поэтому `users`, `delivery_orders`, `assignments` и `outbox_messages` недоступны на уровне прав. Внешних ключей между базами нет.

**Контакты — событиями.** Email и язык получателя приходят событием `user.contact_changed` в поток `events.contacts`; сервис хранит их в `recipient_contacts` и `channel_bindings`. Общего доступа к таблицам пользователей нет, поэтому смена почты видна сервису без синхронного вызова.

**Один активный отправитель.** Режим задавал `config/notifications.php` ключом `driver` (`NOTIFICATIONS_DRIVER`: `local` или `service`), значение читал enum `DeliveryMode`; `AppServiceProvider` выбирал слушателя, шину и источник данных админ-страниц. Переключения нет — режим снят в M12 (см. врезку выше).

**Схемы в одном экземпляре.** JSON Schema контрактов лежат в `contracts/notifications/` и читаются обоими приложениями; сервис получает каталог монтированием только для чтения — копий нет.

**Служебный API — только для админки.** Журнал, ручной повтор и журнал push доступны по `/api/v1/**` под сервисным токеном; монолит обращается к ним из админ-страниц, HTTP-путь заказа сервис не вызывает.

## Альтернативы и причины отказа

| Альтернатива | Почему отказались |
|---|---|
| Сервис читает базу монолита | Это общая база под другим именем: схема заказов становится контрактом для сервиса, миграции одного приложения ломают другое, а персональные данные доступны шире, чем нужно |
| Монолит отдаёт контакты по HTTP | Синхронный вызов в пути отправки связывает доступность сервиса и монолита; событие смены контактов даёт ту же информацию без ожидания и без повторов запроса |
| Общая база с отдельной схемой | Формально разные схемы, фактически один экземпляр: общие права, общий бэкап и общий отказ. Роль без `CONNECT` к базе монолита даёт настоящую границу |
| Два отправителя одновременно с долей трафика | Два источника истины и две записи в разных журналах; сравнение результатов и откат усложняются, а «ровно один эффект» перестаёт проверяться |
| Автоматический fallback на локальный путь | Скрывает сбой сервиса и создаёт дубли: часть событий уходит одним путём, часть другим. Отказ виден в `/health`, лаге и необработанных, а уведомления накапливаются |
| Синхронный вызов сервиса из HTTP-пути заказа | Ответ API ждал бы отправки, сбой сервиса ломал бы создание заказа. Outbox и поток событий развязывают эти операции |
| Отдельные копии JSON Schema в каждом проекте | Копии расходятся; контрактный тест проверял бы копию, а не реальный формат. Один каталог — единственный экземпляр истины |
| Сразу удалить локальный путь M7 | Переход без возможности сравнить поведение и откатиться; на M11 нужен проверяемый переходный период с одним активным отправителем |

## Последствия и цена

Плюсы:

- каналы, шаблоны и журнал меняются без релиза монолита;
- базы независимы: нагрузка и сроки хранения уведомлений не влияют на заказы;
- персональные данные идут отдельным потоком и не попадают в события заказа и в журналы;
- сбой сервиса не ломает заказы: события накапливаются в Outbox и потоке;
- ровно один отправитель в каждый момент, взаимоисключение проверяется guard-тестами.

Цена:

- две базы, две цепочки миграций и два набора тестов;
- тексты шаблонов дублируются в монолите (режим `local`) и в сервисе до M12;
- init-скрипт создания базы и роли выполняется только на пустом томе `pgdata`; на существующем томе операторы выполняются вручную;
- режим переключается переменной окружения и перезапуском процессов, «горячей» смены нет;
- локальный режим заморожен: новый функционал в нём не появляется, флаг и локальный путь удаляются первым шагом M12;
- реального push-провайдера и Telegram на M11 нет: канал push работает через `FakePushProvider`, тексты и предпочтения — M12;
- сервис требует отдельного мониторинга: `/health`, лаг и pending, журнал в stderr.
