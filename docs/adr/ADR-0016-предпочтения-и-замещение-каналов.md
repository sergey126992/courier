## Контекст

На M11 каналы задавала матрица «тип события + роль», порядок отправки не был задан, а «когда отправлять» определяли только попытки и backoff. M12 добавляет три вещи, которых матрица выразить не может:

- человек выбирает каналы по типам событий и окно, в которое его не беспокоят;
- канал может быть недоступен по причинам, которые не лечатся повтором (чат удалён, бот заблокирован, привязка отозвана);
- у провайдера может быть своя плановая задержка (лимит частоты Bot API), не совпадающая с рядом backoff сервиса.

Действуют и ограничения M11: у монолита нет доступа к базе сервиса, служебный API — единственный синхронный канал, журнал отправок живёт в базе сервиса со своим сроком хранения.

## Решение

**Предпочтения живут только в сервисе.** Источник истины — `notification_preferences` (строка на пару «пользователь — тип события»). Монолит их не хранит, не кэширует и не вычисляет: экран настроек читает через служебный API. Решение «куда и когда отправлять» принимается в сервисе, поэтому второе хранилище разошлось бы с первым, а сброс кэша потребовал бы синхронного вызова в пути заказа.

**Дефолт — матрица M11.** Строки нет — действуют каналы матрицы для роли получателя; `NotificationPolicyFactory` остаётся единственным местом дефолта, копий матрицы в домене и в API нет. `critical_override` — служебная метка о том, что email критичного события сервис оставил принудительно.

**Порядок каналов задаётся конфигурацией.** Цепочка `push → telegram → email` и предел длины — параметры `notifications.preferences.channel_priority` и `max_fallback_depth`, не данные пользователя и не код: порядок — операционное решение окружения, email остаётся последним, смена порядка не требует миграции. Пользователь выбирает состав каналов, но не приоритет.

**Замещение — штатное поведение, а не аварийный режим.** Граница проходит по классу ошибки:

- детерминированный отказ канала (нет чата, привязка отозвана, `400`/`403` Bot API, отказ провайдера) переводит строку в `failed`, после чего создаётся строка следующего канала цепочки со ссылкой `fallback_from_notification_id`;
- инфраструктурный сбой (`429`, `5xx`, таймаут, сеть) оставляет строку в `error` и лечится повтором по backoff.

Смысл границы: повтор имеет шанс на успех только при временном сбое; если канал недоступен по существу, повтор лишь отложил бы доставку, а письмо вместо сообщения в мессенджере — такая же ошибка, как потеря. Коды замещения вынесены в `fallback_error_codes`: новый канал не требует правки `ChannelFallback`. Повторный эффект исключён ключом дедупликации `(event_id, recipient_id, channel)`, глубина считается по ссылкам (`FallbackChain`) — отдельная колонка не нужна.

**`deferred_until` и `next_attempt_at` хранятся в строке журнала.** Оба значат «не раньше момента»: `deferred_until` — конец окна тихих часов, `next_attempt_at` — задержка провайдера (`retry_after`). Значение фиксируется при создании строки или отказе и не пересчитывается: вычисление окна при выборке давало бы «плавающее» решение, а хранение в строке делает его наблюдаемым и воспроизводимым.

**Структура `jsonb` валидируется приложением, а не CHECK.** В базе только дешёвые проверки формы: `jsonb_typeof(channels) = 'array'`, `quiet_hours` — `object` либо `NULL`; состав каналов, локаль, окно и критичность проверяет доменный `PreferenceValidator`. Полный CHECK переписывался бы при каждом аддитивном изменении формата, не покрывается unit-тестами и ломает миграцию, а бизнес-правила отвечают `422`.

**Роль передаётся в API предпочтений (`?role=`).** Набор «роль → доступные типы событий» задаёт конфигурация сервиса, монолит получает отфильтрованный набор; иначе перечень пришлось бы держать в двух приложениях. Без параметра API отдаёт объединение наборов — служебный сценарий.

## Альтернативы и причины отказа

| Альтернатива | Почему отказались |
|---|---|
| Хранить предпочтения в монолите и передавать их в событии | Второй источник истины: смена настроек не доходит до уже опубликованных событий, а сервис обязан доверять данным события. Синхронный вызов из события вернул бы зависимость доставки от доступности монолита |
| Кэшировать предпочтения в монолите | Кэш расходится с сервисом, а инвалидация требует обратного вызова; выигрыш нулевой, потому что экран читает настройки один раз на открытие |
| Задавать порядок каналов в предпочтениях пользователя | Пользователь выбирает состав, а не инфраструктурный приоритет; хранение порядка потребовало бы ещё одного формата `jsonb` и валидации, а email всё равно обязан остаться последним |
| Запускать замещение при любой окончательной ошибке | Письмо может подменить сообщение в мессенджере при временном сбое, а причина «канал недоступен» перестаёт отличаться от «провайдер прилёг» (решение 12.1 по вопросу 1) |
| Повторять отправку до исчерпания попыток без замещения | При отозванной привязке повторы бессмысленны и задерживают доставку; пользователь узнаёт о проблеме позже, чем мог бы |
| Хранить глубину цепочки отдельной колонкой | Дублирует данные: глубина выводится из ссылок, а рассинхронизация потребовала бы отдельной сверки. `FallbackChain` считает её за обход длиной не больше предела |
| Вычислять окно тихих часов при выборке | Решение «отложить» менялось бы задним числом при правке настроек, а два прохода поллера могли бы дать разные ответы (FR-NTF-497) |
| Полный CHECK на состав `channels` и ключи окна | Требует правки миграции при каждом аддитивном изменении, не покрывается unit-тестами и отвечает ошибкой базы вместо `422` с кодом причины |
| Отдавать в API все типы событий и фильтровать в монолите | Перечень «роль → типы событий» пришлось бы дублировать в монолите; изменение матрицы требовало бы релиза обоих приложений |
| Отдельный набор эндпоинтов предпочтений на роль | Умножает маршруты и валидацию; один маршрут с необязательным параметром даёт тот же результат |

## Последствия и цена

Плюсы:

- настройки получателя влияют на отправку в одном месте — там, где решается канал;
- монолит без второго хранилища: экран настроек — тонкий клиент служебного API;
- детерминированная недоступность не тратит попытки и не задерживает доставку, а отложенность и задержка провайдера видны в журнале и проверяются тестами без ожиданий;
- порядок каналов и пределы цепочки меняются без релиза кода, схема расширяется без миграции на состав каналов.

Цена:

- экран настроек зависит от сервиса: при отказе данные не показать и не изменить, а синхронное общение требует второго маршрута (служебный API) и защиты токеном;
- правила валидации живут в приложении: схему нельзя проверить взглядом на базу — нужны guard-тест и тесты валидатора;
- глубина цепочки считается обходом ссылок — несколько чтений по идентификатору на редком отказе;
- конфигурация растёт: порядок цепочки, предел глубины, коды замещения, критичные события и наборы событий по ролям;
- счётчики замещения и отложенных живут в памяти процесса и не переживают перезапуск: их экспорт — M13.
