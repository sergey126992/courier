## Контекст

На M7 транспорт был локальной шиной в процессе монолита. После выделения уведомлений в отдельное приложение событие пересекает границу процесса — нужен посредник с подтверждением, повторной выдачей и наблюдаемым отставанием. Требования к нему:

- событие не теряется, если потребитель упал между эффектом и подтверждением, а неподтверждённое сообщение выдаётся повторно;
- лаг и объём неподтверждённых сообщений измеримы для `/health`;
- транспорт заменяем: контракт не диктует брокера;
- в стеке уже есть PostgreSQL и Redis — новый компонент инфраструктуры ради этапа не вводится;
- доставка «хотя бы один раз», порядок событий одного агрегата не гарантируется.

## Решение

**Контракт.** `App\Services\Events\Contracts\EventBus` объявляет `publish`, `consume`, `ack` и `reclaim`. `consume` и `reclaim` принимают обработчик и возвращают `ConsumeResult` со счётчиками `read`, `processed`, `acknowledged`, `failed`, `invalid`, списком идентификаторов и признаком `degraded`. Домен и операции зависят только от контракта.

**Транспорт по умолчанию — Redis Streams.** `RedisStreamEventBus` публикует `XADD`, читает пачкой `XREADGROUP`, подтверждает `XACK` только после фиксации эффекта и возвращает зависшие сообщения `XAUTOCLAIM` после `pending_idle_seconds`. Consumer group создаётся идемпотентно: ответ `BUSYGROUP` не считается ошибкой.

**Потоки и группы.** Имена потоков заданы конфигурацией `events.streams` (`events.orders`, `events.contacts`, `events.notifications`), префикс `events.stream_prefix` изолирует окружения на общем Redis. У монолита и сервиса независимые группы и имена потребителей, поэтому отметки о прочтении потоков не конфликтуют.

**Заменяемость.** `events.transport` выбирает реализацию: `redis` (по умолчанию) или `in-memory` (`LocalEventBus`, тесты и локальный путь M7). Неизвестное значение — ошибка конфигурации. Адаптер RabbitMQ зарезервирован под M13: добавляется новая реализация контракта, домен и операции не меняются.

**Outbox — источник истины.** Публикатор ставит `published_at` только после того, как транспорт принял сообщение; сбой `XADD` оставляет строку и повторяется по backoff. Redis не является источником истины: удаление потока означает лишь отсутствие подтверждения.

**Контракты проверяются до публикации.** `JsonSchemaValidator` читает единственный каталог `contracts/notifications/` и проверяет конверт вместе с payload; несовпадение оставляет строку в Outbox с кодом причины, а не теряет событие.

## Альтернативы и причины отказа

| Альтернатива | Почему отказались |
|---|---|
| RabbitMQ сразу | Требует нового компонента инфраструктуры, управления очередями и DLQ; Redis уже в стеке, а контракт `EventBus` позволяет перейти на RabbitMQ в M13 без правок домена |
| Redis Pub/Sub | Нет consumer group, подтверждения и повторной выдачи: сообщение, отправленное без подписчика, теряется навсегда |
| Kafka | Избыточна для этапа: отдельный кластер, операционная нагрузка и компетенции без выгоды при текущем объёме |
| `LISTEN/NOTIFY` в PostgreSQL | Нет групп потребителей, подтверждений и pending; ограничение размера payload и поведение при обрыве соединения не годятся для надёжной доставки |
| Очередь Laravel как транспорт | Очередь принадлежит одному приложению: два независимых потребителя, группы и лаг потока не выражаются её моделью |
| Прямой HTTP-вызов сервиса на каждое событие | Синхронная связность, повторы и потеря событий при недоступности; Outbox и поток дают развязку и повторяемость |
| Отдельный поток на каждый тип события | Больше потоков, групп и настроек без выгоды: маршрутизация по домену (заказы, контакты, обратные события) достаточна |

## Последствия и цена

Плюсы:

- подтверждение после эффекта и повторная выдача дают «хотя бы один раз» без потерь;
- лаг и pending измеримы: `/health` сервиса и `outbox:status` монолита показывают отставание;
- замена транспорта не требует правок домена и операций (arch-тест контракта);
- потоки разделяют персональные данные и события заказа;
- недоступность Redis не роняет потребитель: проход возвращает `degraded`.

Цена:

- Redis не источник истины: потерянный поток остаётся в Outbox и публикуется повторно;
- дубли допустимы: потребитель идемпотентен — Inbox, `notification_dedup`, уникальные индексы;
- порядок не гарантируется: проекция статусов опирается на `source_event_id`;
- поток общий для окружений — нужен префикс имён;
- «зависшее» сообщение повторяется только после `pending_idle_seconds`: малое значение даёт дубли, большое — задержку восстановления;
- отдельного хранилища мёртвых писем нет: недействительные конверты помечаются `invalid` и подтверждаются;
- переезд на RabbitMQ в M13 добавит адаптер и его эксплуатацию, не меняя контракт, реестр событий и схемы.

## Актуализация (M13)

Решение не пересматривается: Redis Streams — транспорт по умолчанию, RabbitMQ добавлен опцией под профилем compose `broker`. Уточнения по факту реализации:

- **Реализованы оба адаптера под существующие контракты.** В монолите — `App\Services\Events\RabbitMqEventBus` (`publish`, `consume`, `ack`, `reclaim`), в сервисе — `RabbitMqEventStream` (`EventStream`) и `DeadLetterRedriver`; домен, Actions и слушатели не изменились (`TransportGuardTest`, arch-тесты).
- **Выбор — только конфигурацией.** `EVENTS_TRANSPORT` и `NOTIFICATIONS_TRANSPORT` принимают `redis` (по умолчанию) и `rabbitmq`; неизвестное значение останавливает процесс ошибкой конфигурации. «Горячего» переключения через интерфейс нет.
- **Клиент `php-amqplib` v3 требует `ext-sockets`.** Библиотека — чистый PHP без `ext-amqp`, но сокетный транспорт опирается на `sockets`; образы обоих приложений ставят расширение в `docker-php-ext-install`. Без него брокер недоступен, публикация в Redis работает.
- **Топология.** Exchange `topic`, ключ «домен + полный тип события» (`orders.order.created`), привязка `<домен>.#`, очередь `<поток>.<группа>`, `prefetch`, `ack` после COMMIT, `nack`/`requeue` при инфраструктурной ошибке, TTL сообщения и очереди, DLX и DLQ. Имена — из конфигурации.
- **DLX не второй источник истины.** Сообщение из DLX возвращается в основной поток (`DeadLetterRedriver`, счётчик `x-redriven`), дальше работают Inbox, дедупликация и `dlq_entries` при терминальном отказе канала. Отдельной модели разбора нет (см. [ADR-0017](ADR-0017-dlq-и-метрики-сервиса.md)).
- **Паритет подтверждён тестами.** `services/notifications/tests/Feature/TransportParityTest.php` и `tests/Feature/Async/TransportParityTest.php` прогоняют один набор кейсов (публикация → потребление → `ack` → `reclaim` → повтор → DLX/DLQ → деградация) против Redis и RabbitMQ; кейсы RabbitMQ требуют профиля `broker`, без него пропускаются. Расхождение поведения — дефект.
- **Недоступность брокера не роняет публикатор.** `published_at` не ставится, повтор — по backoff, `/health` показывает `degraded`, `notifications:broker-health` — состояние соединения, очередей и DLQ. Секреты не попадают в журнал, метрики, ошибки и DLQ.
- **Цена перехода прежняя**: второй компонент инфраструктуры, эксплуатация очередей и DLX, отдельный прогон CI. Критерии — объём событий и потребность в маршрутизации, TTL сообщения и отдельной очереди мёртвых писем.
