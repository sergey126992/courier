> Актуализация (2026-11): стек обновлён до Livewire 4 — см. [ADR-0018](ADR-0018-обновление-стека.md). Решение ниже описывает выбор серверного интерфейса, а не версию Livewire, и остаётся в силе.

## Контекст

К началу M9 были готовы доменные операции и HTTP API на токенах Sanctum, но пользовательских экранов не было: браузер получал JSON, а ссылки из писем и публичный трекинг вели в API.

M9 даёт браузерный путь целиком: регистрация → письмо → подтверждение → вход → кабинет → заказ → отслеживание, диспетчеру — очередь и назначение курьера. Ограничения этапа:

- интерфейс должен работать без API-клиента и без отдельного фронтенд-приложения;
- доменные операции, права и форматы ошибок не дублируются;
- существующие API-контракты и их тесты остаются без изменения поведения;
- браузерные тесты (Dusk/Playwright) не добавляются — проверка ручная и фиксируется в [11-Интерфейс.md](../11-Интерфейс.md);
- литералов и `env()` в шаблонах нет, значения интерфейса живут в `config/ui.php`.

## Решение

| № | Решение | Что означает |
|---|---|---|
| 1 | Серверный интерфейс на Blade + Livewire 3 + Alpine.js без SPA | Blade отдаёт готовую страницу, Livewire выполняет действия и частичное обновление, Alpine отвечает только за локальное поведение оболочки (тема, drawer, модальные окна, вкладки). Клиентского роутинга и второго слоя состояния нет |
| 2 | Сессионный вход через guard `web`; токены Sanctum остаются для API | Веб-вход открывает сессию и не выдаёт токен. Модель `User` и роли общие, отдельной таблицы аутентификации нет |
| 3 | Одна операция проверки учётных данных — `App\Actions\Identity\AuthenticateUser` | Сравнение пароля, выравнивание времени ответа на несуществующий email и подсчёт неудач живут в одном классе. `LoginUser` вызывает её и выдаёт токен, `LoginForm`/`LoginController` — и открывают сессию |
| 4 | Ссылки из писем и публичная ссылка трекинга ведут на HTML-маршруты, поведение API по умолчанию сохраняется | `VerifyEmailMail`, `ResetPasswordMail` и `CreateTrackingLink` принимают необязательное имя маршрута; без параметра остаются прежние `verification.verify`, `auth.password.reset` и `tracking.public`. Веб подставляет имена из `config('ui.links.*')` и `config('ui.tracking.public_route')` |
| 5 | Чтения — через query-объекты, общие с API | `OrderListQuery` и `DispatcherQueueQuery` используются и `OrderController::index`, и Livewire-компонентами; фильтры проверяются общими классами `OrderFilterRules`, `OrderPayloadRules`, `EstimatePayloadRules` |
| 6 | Интерфейс не ходит в собственный HTTP API | Страницы и Livewire вызывают Actions, Services, query-объекты и политики напрямую; HTTP-слой нужен только внешним клиентам |

Ошибки веба — HTML-страницы `resources/views/errors/*`: `ProblemRenderer` подключён глобально, но возвращает `null` вне `api/*`. Порядок middleware в `bootstrap/app.php` ставит `Authenticate` перед `SubstituteBindings`, поэтому гость получает 302 на вход и не отличает существующий заказ от несуществующего. Роль без доступа отсекается на маршруте (`403`), чужой объект превращается в тот же `404`, что и отсутствующий.

## Альтернативы и причины отказа

| Решение | Альтернатива | Почему отказались |
|---|---|---|
| Blade + Livewire 3 + Alpine | SPA на Vue/React с API-клиентом | Потребовала бы второй сборки, клиентского роутинга, хранения состояния и повторной реализации прав; выгоды нет, а API уже существует |
| Blade + Livewire 3 + Alpine | Классические контроллеры и полные перезагрузки страниц | Каждая фильтрация, автообновление очереди и отмена заказа требовали бы отдельного маршрута и ручного восстановления состояния; Livewire даёт это без дублирования разметки |
| Сессионный guard `web` | Единый вход по токену Sanctum и в браузере | Хранение токена в браузере усложняет защиту cookie и выход; сессия уже настроена (Redis) и не создаёт сущностей доступа |
| Сессионный guard `web` | Отдельная таблица или guard для веба | Вторая модель пользователей и ролей разошлась бы с API; роли и политики остались бы двумя копиями |
| Общая операция `AuthenticateUser` | Своя проверка пароля в веб-входе | Две копии сравнения пароля неизбежно расходятся по тексту ошибки, времени ответа и подсчёту неудач — это прямо запрещено FR-UI-102 |
| Общая операция `AuthenticateUser` | Отдельный сервис только для веба с общим хешированием | Проверка пароля осталась бы в двух местах; выравнивание времени и лимит пришлось бы дублировать |
| Необязательное имя маршрута в письмах и ссылке трекинга | Заменить значения по умолчанию на HTML-маршруты | Сломало бы контракт API и существующие тесты `EmailVerificationTest`, `PasswordResetTest`, `TrackingLinkTest`; обратная совместимость вызовов без параметра дешевле |
| Необязательное имя маршрута | Отдельные классы писем и ссылок для веба | Дублирование шаблонов писем и подписи ссылок; расхождение поведения при правке одного класса |
| Общие query-объекты | Отдельные выборки для Livewire | Фильтры и порядок разошлись бы с API, а бюджеты SQL пришлось бы доказывать дважды; arch-тест запрещает `DB::` в `App\Livewire` |
| Общие классы правил валидации | Свои правила в Livewire-формах | Расхождение правил между API и вебом недопустимо: одно и то же поле принималось бы в одном входе и отклонялось в другом |
| Прямой вызов Actions и query-объектов | HTTP-запрос из веба в собственный API | Лишний сетевой слой, повторная авторизация и невозможность отдать HTML-страницу без второго рендера; ошибки домена пришлось бы переводить из JSON |

## Последствия и цена

Плюсы:

- один набор доменных операций, прав и правил обслуживает API и интерфейс — расхождение исключено;
- ссылки из писем и публичный трекинг открываются в браузере, при этом API сохраняет прежние адреса и контракты;
- страницы отдают готовый HTML, поэтому работают без JavaScript для навигации и форм, отправленных обычным POST;
- интерфейс проверяется быстрыми feature-, Livewire-, компонентными и arch-тестами без браузера и сети.

Цена:

- состояние дублируется между адресом страницы и свойствами Livewire (`#[Url]` у фильтров): новый фильтр правится в двух местах;
- серверные действия идут отдельным HTTP-запросом Livewire: автообновление очереди и трекинга требует `wire:poll` с интервалом из конфигурации;
- Alpine отвечает только за локальное поведение, но фокус-ловушка, drawer и вкладки требуют собственного кода в `resources/js/app.js` и не покрыты браузерными тестами;
- ошибки страницы и формы живут в разных местах (`errors/*` и сообщения компонентов): тексты в `lang/ru` держатся согласованно;
- совместимость писем и ссылок достигается необязательными параметрами: в сигнатурах есть ветвление «веб/API», учитываемое при правках.
