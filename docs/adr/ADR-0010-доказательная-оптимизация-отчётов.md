# ADR-0010. Доказательная оптимизация отчётов

| Поле | Значение |
|---|---|
| Статус | принято |
| Дата | 2026-11 |
| Этап | M8 (отчёты и производительность) |
| Требования | FR-RPT-161…172, раздел 7 ЧТЗ «Отчёты и производительность» |
| Связанные документы | [Отчёты и производительность](../10-Отчёты.md), [Артефакты производительности](../Производительность/README.md), [Отчёт по заказам](../Производительность/Отчёт-по-заказам.md), [Схема данных](../02-Схема-данных.md), [ADR-0004](ADR-0004-целостность-заказов.md) |

## Контекст

Отчёт считает агрегаты по трём таблицам: `delivery_orders`, `assignments`, `courier_shifts`. На наборе 100 000 заказов запрос без индексов идёт полным обходом: один `Seq Scan on assignments`, четыре `Seq Scan on delivery_orders`, 40 034 + 6 044 buffers, около 276 мс.

Ограничения этапа:

- отчёт обязан укладываться в два SQL и не перебирать строки в PHP;
- p95 на наборе 100 000 заказов — не выше 300 мс;
- новых таблиц, read-model и кэша агрегатов на этапе нет;
- существует набор индексов предыдущих этапов: `(transport_type, status)`, `(sender_id, created_at DESC)`, `(status, created_at DESC)` в `delivery_orders`, `(order_id, id DESC)` и `(courier_id, assigned_at DESC)` в `assignments`, exclusion constraint и `(courier_id, started_at DESC)` в `courier_shifts`;
- индекса по `assignments.delivered_at` нет, хотя именно по нему отчёт отбирает вручения.

Нужно было решить, как пополнять набор индексов: по ожиданиям («по времени обычно нужен btree») или по замерам.

## Решение

**Индекс добавляется только по доказанной пользе.** Миграция `2026_11_05_120001_add_reporting_indexes.php` создаёт ровно два индекса:

| Индекс | Определение | Доказательство |
|---|---|---|
| `delivery_orders_requested_at_brin_index` | `USING brin (requested_at)` | BRIN-сканирование 27 940 строк за 0.043 мс и 2 buffers; общий объём чтения отчёта падает с 46 078 до 25 993 buffers |
| `assignments_delivered_at_partial_index` | `(delivered_at) WHERE status = 'delivered'` | индексное сканирование 50 000 нужных строк за 1.595 мс и 128 buffers вместо полного обхода `assignments` в 1 725 buffers |

Доказательство — по трём метрикам сразу: план «до/после», время и `buffers`. Решающая — `buffers`: время на пересозданных наборах гуляет на десятки миллисекунд, а число прочитанных страниц устойчиво. На серии из одного набора `buffers` падают с 33 066 до 24 517 (−26 %), median — с 189.512 до 179.848 мс; p95 полных прогонов — 159–167 мс при пределе 300 мс.

**Отклонённые кандидаты остаются отклонёнными.** `(transport_type, requested_at)` и `(courier_id, delivered_at)` планировщик не выбирает; `courier_shifts (started_at, ended_at)` выбирается, но экономит половину миллисекунды на фоне ~190 мс. В миграцию они не попали и «на будущее» не оставлены.

**Существующие индексы не пересматриваются.** Очередь диспетчера и кабинет отправителя используют `delivery_orders_status_created_index` и `delivery_orders_sender_created_index`: замер подтверждает, новых не требуется. Ни один существующий индекс этап не удаляет и не заменяет.

## Альтернативы и причины отказа

| Альтернатива | Почему отказались |
|---|---|
| Индексы «на всякий случай» по всем колонкам фильтров | Требование FR-RPT-169 прямо запрещает индексы без доказанной пользы: каждый индекс замедляет запись и занимает место. Замер показал, что два из трёх кандидатов планировщик даже не выбирает |
| btree по `delivery_orders(requested_at)` вместо BRIN | Колонка растёт по времени, а отчёт читает диапазон; BRIN дешевле по размеру и записи и уже используется в проекте для `tracking_points.recorded_at`. Отдельный замер btree не проводился: выбран тип, соответствующий характеру колонки |
| Составной индекс `(transport_type, requested_at)` | Разрез по транспорту считается по трём строкам уже после агрегации; планировщик кандидата не выбрал, `Execution Time` остался 240.278 мс при 44 642 + 1 436 buffers |
| Индекс `(courier_id, delivered_at)` | Отбор вручений идёт по времени, а не по курьеру; кандидат не выбран, план стал худшим в серии — 363.656 мс и 43 362 + 2 716 buffers |
| Индекс смен `(started_at, ended_at)` | Выигрыш около 0.5 мс (0.356 мс против 0.855 мс у полного обхода смен), а индекс поддерживается при каждой записи смены. Цена выше пользы |
| Кэш агрегатов, проекция или read-model | Кэш даёт устаревшие числа на границах периода и требует инвалидации на каждой записи заказа, назначения и смены; проекция добавляет согласованность, пересчёт и отставание. Объём данных этапа этого не требует, а решение уже зафиксировано в ЧТЗ (раздел 12.1) |
| Материализованное представление по периоду | Период задаётся запросом, поэтому представление пришлось бы пересобирать под каждый набор границ — это дороже, чем один агрегатный запрос |
| Отказ от индексов вовсе | Без индексов отчёт укладывается в 276 мс, но buffers вдвое выше, а запас до предела 300 мс мал; индексы дают устойчивое снижение чтения без изменения кода |
| Настройка `work_mem` / JIT под отчёт | Меняет глобальные параметры сервера ради одного запроса; замер и так идёт с `SET jit = off`, чтобы время не зависело от LLVM. Параметры стенда не переносятся на прод |
| Замена `delivery_orders_status_created_index` на `(status, created_at DESC, id DESC)` | Существующий индекс обслуживает и другие запросы; польза замены не замерялась, а очередь укладывается в 7.793 мс при 3 709 buffers |

## Последствия и цена

Плюсы:

- отчёт укладывается в p95 159–167 мс при пределе 300 мс и читает вдвое меньше страниц;
- в миграции нет ни одного индекса, польза которого не показана планом;
- артефакты лежат в репозитории и воспроизводятся одной командой, поэтому решение можно перепроверить, а не принимать на веру;
- откат миграции снимает ровно два индекса и не трогает существующие.

Цена:

- каждый индекс замедляет запись: BRIN — дёшево, частичный btree по `assignments(delivered_at)` обновляется при каждом вручении;
- частичный индекс работает только для условий, совместимых с `WHERE status = 'delivered'`; запрос без этого условия его не использует;
- отчёт всё равно делает до трёх полных обходов `delivery_orders` (отмены, валюты, соединение вручённых) — при росте данных это первое место для следующего замера;
- замер зависит от стенда: числа нельзя переносить на прод как обещание, переносится только метод;
- расширение отчёта (новый фильтр, разрез по отправителям) требует нового замера «до/после».

## Как проверить

```sh
# планы «до/после» на наборе по умолчанию
docker compose exec app php artisan reporting:benchmark --explain

# замер без индексов и с временными кандидатами на одном наборе
docker compose exec app php artisan reporting:benchmark --runs=30 --json
docker compose exec app php artisan reporting:benchmark --runs=30 --json --with-indexes
```

1. `--explain` печатает `EXPLAIN (ANALYZE, BUFFERS)` для отчёта, загрузки курьеров, очереди диспетчера и кабинета отправителя; планы снимаются по тем же текстам SQL, что выполняет приложение.
2. `sql_queries` в выводе должен быть равен 2: сводный агрегат и секунды смен.
3. `metrics_ms.p95` на наборе 100 000 заказов должен оставаться ниже 300 мс.
4. Наличие и обратимость индексов проверяет тест `tests/Feature/Reporting/ReportingIndexesMigrationTest.php`: после отката индексов нет, существующие индексы таблиц на месте, повторный `migrate` проходит.
5. Артефакты для сравнения — `storage/app/benchmark/timed-*.txt` (один набор, все стадии) и `after.txt`, `candidate-base.txt` (планы).
