# ADR-0006. Целостность диспетчеризации

| Поле | Значение |
|---|---|
| Статус | принято |
| Дата | 2026-11 |
| Этап | M5 (диспетчеризация) |
| Требования | FR-DSP-103, FR-DSP-134…139, раздел 7 ЧТЗ «Диспетчеризация и трекинг» |
| Связанные документы | [Диспетчеризация](../07-Диспетчеризация.md), [Схема данных](../02-Схема-данных.md), [ADR-0004](ADR-0004-целостность-заказов.md) |

## Контекст

Диспетчеризация вводит два инварианта, которые нельзя нарушать ни при каких запросах:

- у курьера не может быть двух смен, интервалы которых пересекаются;
- у заказа и у курьера одновременно не может быть двух активных назначений («назначено», «принято», «забрано»).

Оба инварианта проверяют домен и операции, но проверка в коде не спасает от гонки: два диспетчера одновременно назначают курьера, курьер дважды открывает смену, запрос приходит между `SELECT` и `INSERT`. Отдельно нужно было решить, что будет при удалении пользователя или заказа со сменами, назначениями и точками.

Ограничения:

- домен остаётся чистым и не знает о базе;
- клиент получает понятный код ошибки, а не 500 при нарушении ограничения;
- история попыток назначения и ленты геоточек не перезаписывается.

## Решение

- Оба инварианта продублированы в схеме:
  - `courier_shifts_period_excl` — `EXCLUDE USING gist (courier_id WITH =, tstzrange(started_at, coalesce(ended_at, 'infinity')) WITH &&)`; для сравнения идентификаторов миграция включает расширение `btree_gist`;
  - `assignments_active_order_unique` и `assignments_active_courier_unique` — частичные уникальные индексы по `order_id` и `courier_id` с условием `status IN ('assigned', 'accepted', 'picked_up')`.
- Домен проверяет то же самое заранее (`ShiftRules`, `AssignmentTransitions`), чтобы клиент получил осмысленный код: `COURIER_SHIFT_ALREADY_OPEN`, `COURIER_SHIFT_OVERLAP`.
- Нарушения целостности переводятся в коды по SQLSTATE: `23P01` (exclusion) — пересечение смен, `23505` (unique) — открытая смена или занятый заказ. Исключение не «всплывает» как 500.
- Строка заказа блокируется на время назначения (`lockForUpdate`), назначение пишет строку и переход статуса в одной транзакции.
- Внешние ключи: удаление пользователя со сменами или назначениями и заказа с назначениями запрещено (`restrictOnDelete`); зона смены обнуляется (`nullOnDelete`) — смена без зоны значит «любая зона».

## Альтернативы и причины отказа

| Альтернатива | Почему отказались |
|---|---|
| Только проверки в домене | Проверка и запись не атомарны: между ними проходит чужой запрос, и оба назначения успешно сохраняются. Инвариант, который держится на дисциплине кода, ломается первой же гонкой |
| Advisory locks на ключ «заказ» и «курьер» | Лок живёт только внутри соединения и требует единой дисциплины захвата во всех сценариях; забытый лок не виден ни тестам, ни схеме. Ограничение базы действует независимо от того, какой код пишет строку |
| Отдельная таблица «текущее назначение» с уникальным ключом | Пришлось бы синхронизировать её с историей попыток: две записи об одном факте, риск расхождения и лишние операции на каждый переход |
| Признак `is_active` в строке назначения с уникальным индексом | Дублирует статус: при переходе нужно менять два поля, а рассинхронизация даёт «активную» строку в терминальном статусе. Частичный индекс по статусу выражает то же самое без второго источника истины |
| Триггеры на переходы и пересечения | Правило переезжает в базу, вне домена и вне модульных тестов; сообщения об ошибке и роли формируются в приложении. Миграция на каждое изменение процесса |
| Блокировка всей таблицы на время назначения | Сериализует всех диспетчеров и курьеров; ограничение по ключу даёт ту же защиту без глобальной очереди |

## Последствия и цена

Плюсы:

- инварианты держатся даже при ошибке в коде, прямом SQL и параллельных запросах;
- клиент получает 409 с понятным кодом вместо 500, потому что SQLSTATE переводится в доменную ошибку;
- частичные индексы не мешают истории: терминальных попыток у заказа может быть сколько угодно;
- пересечение смен описано одним ограничением, а не набором проверок «до/после/во время».

Цена:

- схема привязана к PostgreSQL: `btree_gist`, exclusion constraint и частичные индексы не переносятся на SQLite и MySQL — тестовое окружение тоже PostgreSQL;
- новый активный статус назначения требует правки условия индексов и миграции; забытое условие ослабит защиту (проверяется guard-тестами);
- проверка дублируется: домен и база знают одно правило, и обе копии нужно держать согласованными;
- удаление пользователя или заказа со историей невозможно без предварительной очистки — это осознанный запрет, а не недоработка;
- ошибки целостности приходится разбирать по SQLSTATE, то есть код операции знает о поведении драйвера.
