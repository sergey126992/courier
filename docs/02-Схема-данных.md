# Схема данных

Схема базы приложения (M0–M12): таблицы, ключи, индексы и ограничения, на которые опираются запросы, и отдельная база сервиса оповещений. Слои — [01-Архитектура.md](01-Архитектура.md), API — [03-Доступ-и-роли.md](03-Доступ-и-роли.md), [05-Зоны-и-расстояния.md](05-Зоны-и-расстояния.md), [06-Заказы.md](06-Заказы.md), [07-Диспетчеризация.md](07-Диспетчеризация.md), [08-Трекинг.md](08-Трекинг.md), асинхронность — [09-Асинхронность.md](09-Асинхронность.md), отчётность — [10-Отчёты.md](10-Отчёты.md); решения — [ADR-0004](adr/ADR-0004-целостность-заказов.md), [ADR-0006](adr/ADR-0006-целостность-диспетчеризации.md), [ADR-0008](adr/ADR-0008-публикатор-outbox-и-inbox.md), [ADR-0009](adr/ADR-0009-каналы-уведомлений.md), [ADR-0010](adr/ADR-0010-доказательная-оптимизация-отчётов.md), [ADR-0014](adr/ADR-0014-граница-сервиса-оповещений.md), [ADR-0015](adr/ADR-0015-транспорт-событий.md), [ADR-0016](adr/ADR-0016-предпочтения-и-замещение-каналов.md).

Только PostgreSQL 16: функциональные и частичные уникальные индексы, exclusion constraint с `btree_gist` и BRIN используются намеренно. Полный DDL — в `database/migrations/`.

## Общие соглашения

| Соглашение | Как выполнено |
|---|---|
| Моменты времени | колонки этапов M4–M7 объявлены как `timestamptz`; даты без времени (`email_verified_at`, `created_at` служебных таблиц и журналов) — `timestamp` |
| UTC в асинхронном слое | `available_at`, `published_at`, `processed_at` и `sent_at` — `timestamptz`; модели приводят моменты к UTC перед записью, а публикатор и Inbox передают смещение UTC явно |
| Статусы уведомлений | `notifications.status` защищён CHECK по набору `created`, `queued`, `sent`, `error`, `failed`; допустимые переходы живут в домене, а не в базе |
| UTC | модели `CourierShift`, `Assignment` и `TrackingPoint` используют трейт `App\Models\Concerns\ConvertsTimestampsToUtc`: момент приводится к UTC при присвоении атрибута, иначе Eloquent записал бы «местные» часы и сравнения интервалов стали бы неверными |
| Статусы | в таблицах строковые коды с CHECK на набор значений; допустимые пары переходов живут в домене, а не в базе |
| Массовое присвоение | статусных колонок нет в `$fillable`: значение меняется только доменным методом модели (`applyTransition`) |
| Только добавление | `order_status_history`, `tracking_points`, `processed_messages`, `notification_attempts` и `push_messages` не имеют `updated_at`; записи не переписываются |
| Удаление справочников | ссылки на пользователей, зоны и заказы — `restrictOnDelete`: запись с историей не удаляется, справочник деактивируется |
| Техническая очистка | каскад допустим только там, где строка не несёт истории: профили, ключи идемпотентности, последние позиции, попытки отправки |
| Сроки хранения | задаются конфигурацией и удаляются командами по расписанию, а не триггерами: Inbox — 30 дней, журнал уведомлений — 90, попытки — 90, push-журнал — 30; опубликованные строки Outbox не очищаются |

### Диспетчеризация (M5)

| Таблица | Назначение | Ключи и ограничения |
|---|---|---|
| `courier_shifts` | смены курьера | `courier_id` — `restrictOnDelete`; `zone_id` — `nullOnDelete`, `null` означает «любая зона»; `started_at`, `ended_at` (`timestamptz`); exclusion constraint `courier_shifts_period_excl`; индекс `(courier_id, started_at DESC)` |
| `assignments` | попытки назначения курьера на заказ | `order_id` и `courier_id` — `restrictOnDelete`; CHECK `assignments_status_check` по шести статусам; два частичных уникальных индекса; индексы `(order_id, id DESC)`, `(courier_id, assigned_at DESC)` и частичный `assignments_delivered_at_partial_index` по `delivered_at` при `status = 'delivered'` |

Пересечение смен запрещено ограничением базы: интервал `[started_at, coalesce(ended_at, 'infinity'))` одного курьера не может пересекаться с другим интервалом того же курьера:

```sql
EXCLUDE USING gist (courier_id WITH =, tstzrange(started_at, coalesce(ended_at, 'infinity')) WITH &&)
```

Для сравнения идентификаторов в GiST миграция создаёт расширение `btree_gist`; при откате оно удаляется. Момент окончания одной смены не пересекается с моментом начала другой, поэтому смены «встык» допустимы.

Двойное активное назначение отсекается частичными уникальными индексами:

```sql
CREATE UNIQUE INDEX assignments_active_order_unique ON assignments (order_id) WHERE status IN ('assigned', 'accepted', 'picked_up');
CREATE UNIQUE INDEX assignments_active_courier_unique ON assignments (courier_id) WHERE status IN ('assigned', 'accepted', 'picked_up');
```

У заказа и у курьера одновременно может быть только одна строка в активном статусе; терминальных попыток у заказа может быть сколько угодно — история не перезаписывается.
Колонки `assignments`: `status`, `strategy` (фактически применённое правило), `distance_to_pickup_km` (число или `null`), метки этапов `assigned_at`, `accepted_at`, `picked_up_at`, `delivered_at`, `failed_at`, `cancelled_at`, `failure_reason`, `failure_comment`.

### Трекинг (M6)

| Таблица | Назначение | Ключи и ограничения |
|---|---|---|
| `tracking_points` | лента геоточек назначения, только добавление | `assignment_id` — `restrictOnDelete`; CHECK `tracking_points_latitude_check`, `tracking_points_longitude_check`, `tracking_points_source_check`; BRIN по `recorded_at`; индекс `(assignment_id, recorded_at DESC, id DESC)`; без `updated_at` |
| `assignment_last_positions` | последняя позиция назначения | `assignment_id` уникален, `cascadeOnDelete`; CHECK диапазонов координат |
| `courier_last_positions` | последняя позиция курьера | `courier_id` уникален, `cascadeOnDelete`; CHECK диапазонов координат; индекс `recorded_at` для отсева устаревших позиций |

`tracking_points` растёт линейно, поэтому время точки покрыто BRIN (дешевле btree), а лента назначения — btree с убыванием времени и `id` вторым ключом. Источник точки — только `courier`.
Последние позиции обновляются `upsert` по уникальному ключу: строк не больше, чем назначений и курьеров. Позиция назначения удаляется с назначением, курьера — с пользователем (техническая очистка, не история).

### Асинхронность и уведомления (M7)

| Таблица | Назначение | Ключевые поля, ограничения и индексы |
|---|---|---|
| `outbox_messages` (расширение) | исходящие события и состояние публикации | `message_id` уникален и выдаётся базой; `available_at` (`timestamptz`) заполняется приложением; `last_error` — код причины последнего сбоя; частичный `outbox_messages_pending_index` по неопубликованным строкам; CHECK `attempts >= 0` |
| `processed_messages` | Inbox: отметки обработанных событий | `message_id` (uuid), `handler`, `processed_at` (`timestamptz`), `created_at`; уникальный `(message_id, handler)`; индекс `created_at` для очистки; `updated_at` нет |

Локальных таблиц уведомлений (`notifications`, `notification_attempts`, `push_messages`) в монолите нет — ни таблиц, ни миграций, ни моделей; журнал живёт в базе сервиса (раздел «База сервиса оповещений»). Проверяет `tests/Arch/LocalNotificationPathTest.php`.

Схема асинхронного слоя: `message_id` уникален на уровне базы и заполняется при вставке; публикатор выбирает по частичному индексу неопубликованных строк; прежний `(published_at, created_at)` сохранён для метрик; внешнего ключа на агрегат нет (`aggregate_type` и `aggregate_id` — разные таблицы), целостность держат операции;
- сроки хранения — конфигурация и команды по расписанию: Inbox — 30 дней (`processed-messages:purge`), журнал, попытки и push-журнал — в сервисе командой `notifications:purge`; опубликованные строки Outbox не удаляются.

### Отчётность (M8)

Новых таблиц нет: отчёт читает `delivery_orders`, `assignments`, `courier_shifts`. Миграция `2026_11_05_120001_add_reporting_indexes.php` добавляет два индекса, подтверждённых планами «до/после» ([Производительность/](Производительность/README.md), [ADR-0010](adr/ADR-0010-доказательная-оптимизация-отчётов.md)):

| Индекс | Определение | Зачем |
|---|---|---|
| `delivery_orders_requested_at_brin_index` | `USING brin (requested_at)` | сводный запрос дважды отбирает заказы по диапазону `requested_at`; BRIN дешёв по размеру и записи для колонки, растущей по времени |
| `assignments_delivered_at_partial_index` | `(delivered_at) WHERE status = 'delivered'` | отчёт отбирает вручения по `delivered_at`, а индекса по этой колонке не было; частичный индекс хранит только нужные строки |

Оба индекса обратимы: `down()` снимает ровно их и не трогает существующие индексы таблиц. Кандидаты `(transport_type, requested_at)`, `(courier_id, delivered_at)` и `courier_shifts (started_at, ended_at)` отклонены замером и в миграцию не попали. Очередь диспетчера и кабинет отправителя продолжают работать на `delivery_orders_status_created_index` и `delivery_orders_sender_created_index` — новых индексов им не требуется.

### Проекция доставки (M11)

Миграция `2026_11_06_100001_add_correlation_id_to_outbox_messages.php` добавляет в `outbox_messages` колонку `correlation_id` (`varchar(128)`, `NULL`) — идентификатор запроса: `varchar`, а не `uuid`, потому что значение совпадает с `X-Request-Id` и принимает внешний шаблон 8–128 символов. Старые строки остаются `NULL`.

Миграция `2026_11_06_100002_create_order_notification_status_table.php` создаёт проекцию статусов доставки:

| Таблица | Назначение | Ключи и ограничения |
|---|---|---|
| `order_notification_status` | статус доставки по каналам в карточке заказа; заполняется только в режиме `service` из обратных событий | `order_id` — `cascadeOnDelete` на `delivery_orders`; `notification_id` — идентификатор уведомления сервиса без внешнего ключа; `channel`, `status`, `attempt`, `error_code`, `source_event_id` (uuid), `occurred_at` (`timestamptz`); уникальные `notification_id` и `source_event_id`; индекс `(order_id, channel)` |

Правила проекции: одна строка на уведомление — повтор с тем же `source_event_id` вторую не создаёт (уникальные индексы, а не проверка перед вставкой); внешнего ключа на базу сервиса нет (`notification_id` — идентификатор из события); строка удаляется с заказом (`cascadeOnDelete`); своего срока хранения нет.

### База сервиса оповещений (M11–M13)

Сервис — отдельная база `notifications` под ролью `notifications` (init-скрипт `docker/pgsql/init/02-create-notifications-db.sql`, тесты — `notifications_testing`); миграции — `services/notifications/database/migrations/`, в базе монолита не выполняются.

| Таблица | Назначение | Ключи и ограничения |
|---|---|---|
| `notifications` | журнал уведомлений сервиса | уникальный `(event_id, recipient_id, channel)`; CHECK статусов `created`, `queued`, `sent`, `error`, `failed`; `correlation_id` для сквозной трассировки; M12 добавляет `next_attempt_at`, `deferred_until` и `fallback_from_notification_id` |

| `device_tokens` | `user_id`, `token`, `fingerprint`, `platform` | владелец, полный токен (только для отправки), отпечаток для логов, платформа |
| `device_tokens` | `locale`, `app_version`, `last_seen_at`, `revoked_at` | необязательные сведения клиента, момент последней регистрации и отзыва |

Правила сервиса и проверки — в [09-Асинхронность.md](09-Асинхронность.md) и [README сервиса](../services/notifications/README.md): внешних ключей между базами нет (`order_id`, `recipient_id` — из события); дедупликация держится индексами `inbox_messages`, `notification_dedup`, `notifications`; статусы журнала и каналы `channel_bindings` ограничены CHECK, у `notifications.channel` CHECK нет (поэтому `telegram` без миграции); в `notification_preferences` база проверяет только форму `jsonb`, состав и окно — `App\Domain\Notifications\PreferenceValidator`; сроки хранения: `inbox_messages` и `notification_dedup` — 30 дней, `notifications` и `notification_attempts` — 90, `push_messages` — 30, `telegram_link_tokens` — 7 дней после `used_at` или `expires_at`, `dlq_entries` — 90 (команды `notifications:purge`, `notifications:dlq-purge`, `notifications:telegram:purge`), отозванные `device_tokens` — 30 дней без команды очистки; email — только `recipient_contacts` и `channel_bindings`, `chat_id` — в `channel_bindings.address`, в токенах — хеш; роль `notifications` без доступа к базе монолита (`REVOKE ALL ON DATABASE courier`). Схему держат `SchemaGuardTest.php`, `PreferenceSchemaGuardTest.php`, `TelegramSchemaGuardTest.php` (`services/notifications/tests/Feature/`), `tests/Feature/DlqTest.php` и `tests/Feature/DeviceTokenApiTest.php`.
Схему сервиса держат guard-тесты `services/notifications/tests/Feature/SchemaGuardTest.php`, `PreferenceSchemaGuardTest.php` и `TelegramSchemaGuardTest.php`; уникальность `(notification_id, channel)`, индексы выборки DLQ и отсутствие внешнего ключа на журнал проверяет `tests/Feature/DlqTest.php`, поведение уникального `token` и частичного индекса активных токенов — `tests/Feature/DeviceTokenApiTest.php`. Состав и назначение таблиц — в [README сервиса оповещений](../services/notifications/README.md).

## Связи

`users` 1:1 — `sender_profiles`, `courier_profiles`, `courier_last_positions`; 1:м — `role_changes`, `delivery_orders` (отправитель), `courier_shifts`, `assignments` (курьер).
`service_zones` 1:м — `delivery_orders` и `courier_shifts`; `delivery_orders` 1:м — `order_status_history`, `assignments`, `idempotency_keys` (через пользователя); `assignments` 1:м — `tracking_points` и 1:1 `assignment_last_positions`.

`outbox_messages` и `processed_messages` стоят вне этой схемы: `aggregate_id` ссылается на разные агрегаты, а `processed_messages.message_id` — на `outbox_messages.message_id`, но внешнего ключа нет: событие не должно зависеть от срока хранения отметки и наоборот.

`order_notification_status` связана внешним ключом только с `delivery_orders` (`cascadeOnDelete`); локальных таблиц уведомлений в монолите больше нет — журнал и попытки живут в базе сервиса. Базы сервиса оповещений в этой схеме нет: между базами не бывает внешних ключей, связь поддерживают `order_id`, `notification_id` и `source_event_id` из событий (см. [ADR-0014](adr/ADR-0014-граница-сервиса-оповещений.md)).
